# OPEN_WORK: the formal queue, and a todo list it came from

**Two halves, and they are not the same kind of thing.**

1. **THE QUEUE — derived, and it cannot be edited by hand.** The formal section
   below is generated by `python3 tools/formal_doc_index.py --write` from two
   facts about the tree: each document's **area** (the `formal/` file it cites
   most, so a row is grouped by the part of the backend it is in) and its
   **claim status** (`tools/control.py`'s registry, so a row whose worker has
   finished says `unclaimed` rather than naming an owner nobody holds).
   `python3 tools/formal_doc_index.py --check` compares the rendered block with
   the file byte for byte, and `test_suite.py` runs that check — so adding a
   document, deleting one, or a worker starting or finishing turns this file red
   until somebody runs `--write`. **That is the whole point, and it is why the
   hand-maintained table this replaced is gone:** it named documents that had
   been deleted, carried prose nobody re-read, and had no way to notice either.
   It had also drifted from "one row per open item" into a mixture of live rows
   and `*(deleted 2026-10-02)*` rows that explained a fix in three sentences —
   which is a Status history in an index, the one thing an index must not be.
2. **THE TODO LIST (sections A–F below) — hand-maintained, and dated.** It is
   the x86-64 formal brief the queue above grew out of, kept because the
   measurements in it are still the ones to beat. **Its numbers are a claim about
   runs, not about the tree** (`CLAUDE.md` says so and is right), so read them as
   history and re-measure before quoting one.

**Date of the todo list: 2026-09-26.** Everything in sections A–F below was true
of `master` on that date and some of it has since been fixed; where a row says so,
it says so with the commit or the document that says it.

**Scope.** The formal backend (arm64 + x86-64 Mach-O, Lean proofs) and the
shared self-hosting infrastructure it sits on. The arm64 codegen and arm64
proof-generator work is *in* the queue above — it is what most of those documents
are — so the old "not here" paragraph is gone with the table it belonged to.

## E. Method notes worth carrying forward

Not work items — things that were learned the hard way and should not be
re-learned. The generalisation rule, from the x86-64 proof work:

> Generalise a form when the backend actually emits more than one shape of it,
> and not otherwise. `movzx r64, r8` is emitted as the identical `48 0f b6 c0`
> in all 33 instances, so a concrete lemma covers them all and a
> register-parameterised one would be machinery nothing calls. Every form that
> *was* pinned to one register pair, though, turned out to need generalising —
> so it is a heuristic, not a proof.

Three more, each of which cost real time and each of which is a trap that
reappears:

- **A lemma with contradictory hypotheses compiles, typechecks and proves its
  goal.** It is simply inapplicable, so the file is green and the lemma is
  doing nothing — worse than absent, because absent shows up as a gap. Check
  hypotheses are *satisfiable at a real call site*; "the file builds" is
  exactly the signal that misses this.
- **The `sorry` guard must be `try (…) <;> all_goals sorry`**, inside the
  inline `by`. An unsolved goal in a sub-`by` is an *elaboration* error, so
  nothing enclosing it catches it. And `first | a | b` is wrong: `first`
  commits to the first alternative that does not *throw*, not the first that
  *closes the goal*.
- **A heartbeat timeout is not catchable by `try`.** The budget is the only
  lever.
