## What is believed, and why

### The measurement that pins it

A three-line program on the formal path, built with `fire.py build --formal
--no-prove` and RUN:

    def main(n: Int) -> Int:
        a = "\\"
        b = "\n"
        c = "x"
        printf("len(a)=%d len(b)=%d len(c)=%d\n", len(a), len(b), len(c))
        return 0

    $ .tmp/repro/esc.bin
    len(a)=1 len(b)=1 len(c)=1

**A string literal's escapes are decoded.** `"\\"` is ONE character and `"\n"`
is ONE character. That is `24f5b547`'s subject ("a string literal's escapes ARE
decoded"), which is the right answer and CPython's.

### What the suite still assumes

`test_re_formal.py`'s `mojo_str` (line ~307) writes every corpus pattern and
subject into the generated program, and its docstring says:

> A string literal on the formal path is interned VERBATIM and its escapes are
> NOT unescaped, so nothing here is escaped: the pattern text a Python raw
> string holds IS the bytes a Mojo literal must contain, which is why
> `r"\d+"` becomes `"\d+"` and not `"\\\\d+"`.

The premise stopped being true when `9023031b` landed; `24f5b547` fixed the
stale half of that pair in `test_formal_sys.py` and this is the half it missed.
So `mojo_str` writes a Mojo literal whose backslashes the runtime then DECODES:
`r"\bfn\b"` reaches `re` as `<BS>fn<BS>` (backspace, not a word boundary) and
`"\\\\"` reaches `re` as a single `\`.

Every failing case is a pattern containing a backslash, and the six `\b` corpus
cases show it exactly: **the only `\b` case that passes is case 52,
`r"\bcat\b"` on `'concatenate'`, which is the one with no word boundary in it at
all** — a pattern whose answer is "no match" cannot tell a working `\b` from a
broken one. The other five `\b` cases all have a real boundary and all fail.

### The three shapes it produces, decoded

Built and run individually (`.tmp/repro/chunk_50.py`, `.tmp/repro/chunk_88.py`,
both generated by `test_re_formal.py`'s own `program()`, compared against its own
`expected()`):

**`\b` — a word boundary is never asserted** (cases 47, 48, 50, 51, 108). Case
50 is the smallest witness:

    re.search('\b', ' x ', 0)

    got : [-99, 0, -99, 0,   -1, -1, …]        # found = 0, spans blanked
    want: [-99, 0, -99, 1,    1,  1, …]        # found = 1, start = end = 1

and `findall` on the same pattern returns 0 items where CPython returns 2. The
status is `STATUS_NO`, not a refusal: `formal/hostmods/re.mojo`'s `_worb` and
`_isw` are correct and are never reached, because the byte before them is 0x08
and not a backslash.

**VERBOSE `#` comment ends at the wrong place** (case 88). The pattern
`a  # comment\n b` (backslash-n, two characters) with `flags=64`: the form gets
(0,2) and the oracle wants (0,1), because the oracle's pattern has no real
newline so `#` comments to the end, while the program's has one so `#` comments
to it and ` b` becomes significant. Same cause, different symptom — and this one
is a disagreement between the harness and the runtime, not a defect in `re`.

**An escaped backslash is refused** (case 92). `re.search('\\\\', 'a\\b', 0)`:

    got : [-99, 0, -99, 3, -1, -1, …]        # 3 == re.STATUS_UNSUPPORTED()
    want: [-99, 0, -99, 1, 1, 2, …]

Status 3 with the spans blanked is `search`'s `e != 0` arm returning
`_prepare`'s error, and `formal/hostmods/re.mojo:1444`'s "nothing may be LEFT
OVER" check is what sets it: one backslash is not a complete atom. **This is the
one of the three whose residual may be a real `re` gap** — once `mojo_str` is
fixed the pattern will be a genuine escaped backslash, and whether `_p_atom`
compiles one is then the question. It is listed here so the fix does not
discover it by surprise.

## The next step, exactly

**`mojo_str` must emit the INVERSE of the decoder: double every backslash that
is part of the Python string's own text.** One function, in a test file, with a
CPython oracle already sitting next to it — and the suite then says what it was
written to say.

Concretely, in `test_re_formal.py`'s `mojo_str`:

1. Keep the real-newline and real-tab handling exactly as it is. Those arrive as
   real CHARACTERS (`mojo_str` already asserts on them and splits into
   `mk2`/`mk3`), so they are not escapes and need no doubling.
2. For every other `\` in the string, write `\\` — because the literal is
   decoded once on the way in, and one doubling is what makes the byte that
   arrives the byte the Python string holds.
3. Rewrite the docstring's premise. "interned VERBATIM and its escapes are NOT
   unescaped" is now false, and `24f5b547` is the commit that says so.

Then re-run `formal-re`. Six of the seven cases should go green; case 92 either
goes green or leaves a real `re` gap to file, which is the honest outcome.

**Do not "fix" this by making the formal path stop decoding.** The decode is
CPython's behaviour and is pinned by `test_formal_sys.py`; `mojo_str` is the
stale side of the pair.

## Cost note

`formal-re` builds and EXECUTES ~140 images per backend, so a solo run is tens
of minutes on a loaded machine (the `-k corpus_against_cpython` subset is the
