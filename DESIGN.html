DESIGN — Container Typing in Codegen

Why the match_pattern dict-as-list SIGBUS was possible, and the design rules that had to be violated for it to happen.
Written 2026-09-13, from measurements of the tree at commit 5633e87.

The question

"Is all codegen for a Dict in 30 lines of code, trivial to audit? If not — if this is one of thousands of codegen bits for a Dict spread across 9 gimple files — isn't that the bug?"

Answer: it is not 30 lines, and yes — that is the bug.

Container-kind handling is spread over 17 files and 62,851 lines. The dict-versus-list decision is independently re-derived at 239 sites in 12 files, read back at 224 more, and there is no single predicate anywhere that answers "is this value a dict?". The bug that took a full debugging session to find was one of those 239 sites choosing wrong. Nothing in the architecture prevents the other 238 from doing the same, and the fix I landed is not obvious in the code — it lives on one line inside a 907-line function.

Rules violated

R1 · Single source of truth for a type decisionVIOLATED

Rule. A semantic classification — "this value is a dict, not a list" — must be computed by exactly one function. Every consumer calls it. CLAUDE.md already states the general form of this rule: "Consolidate duplicates rather than maintaining parallel implementations. If two files do the same thing, merge them."

Evidence of violation. 239 independent assignment sites across 12 files; zero canonical predicates. The kind is recomputed from scratch — from usage heuristics, from call signatures, from literal shapes, from element maps — in each one.

Consequence. A correct fix must be applied 239 times to be complete, and there is no mechanical way to know whether it was. Each site is an independent opportunity to reintroduce the identical bug.

R2 · Coercion must be partial, and refuse the impossibleVIOLATED

Rule. A type-conversion chokepoint must be able to say no. MojoDict * → MojoList * is not a conversion; the structs are not layout-compatible. It must be a hard, loud compile-time failure naming both types and the source location.

Evidence of violation. _coerce_to_type (gimple_gen_infra.py:2643) delegates to _safe_coerce_emit (gimple_gen_resolve.py:1343), which contains zero raise or assert statements. Repo-wide, no codegen path rejects an impossible type conversion. Every pair of types is silently convertible.

Consequence. This is the single highest-leverage failure. The chokepoint already existed and every argument passed through it. One raise here would have converted a multi-session SIGBUS hunt into a precise error message at the exact moment the bad code was generated: cannot coerce MojoDict * to MojoList * (arg 3 of match_pattern, ast_rewriter.py:672).

R3 · Never emit a cast that defeats the type checkerVIOLATED

Rule. The generated C's type system is a free, exhaustive verifier of this compiler's own reasoning. Emitting a pointer cast switches it off exactly where it would have paid out. Casts may be emitted only by the coercion chokepoint, and only after it has established the conversion is legal.

Evidence of violation. 146 hard container-kind casts, written directly at call sites rather than by the chokepoint. The worst shape, appearing verbatim twice:

gimple_gen_calls.py:1309
gimple_gen_calls.py:1342
    lv = av if at == 'MojoList *' else gen._new_val('MojoList *', f'(MojoList *){av}')

Read plainly: "if it is not already a list, declare that it is one." No check that the source could possibly be a list.

Consequence. GCC compiled the faulting program without a single warning. The emitted C was well-formed and meaningless. Note the contrast: when I removed the cast's protection by hand, GCC immediately caught an unrelated error ('gen' undeclared) in seconds — the checker works, when we let it.

R4 · Absence of evidence is not evidenceVIOLATED — and self-documented

Rule. An inference that cannot prove a property must record "unknown" and degrade to a safe representation. It must never convert "I could not prove this key is a string" into "therefore this container is a list."

Evidence of violation. The codebase states this rule at gimple_gen_infra.py:2114 —

// ... reaching this branch only means "some subscript key could not be
// PROVEN to be a string" — the absence of evidence, not evidence of a
// list. The unambiguous signal has to win, or a dict subscripted with a
// key whose stringness this analysis cannot see through ... is silently
// typed `MojoList *`.

— and then, 25 lines later, does exactly that:

else:
    inferred[pname] = 'MojoList *'          // gimple_gen_infra.py:2139

The comment predicts the bug precisely, including its mechanism. A previous author saw it, patched the one instance in front of them (is_dict_method), and left the default in place.

Consequence. Two single-flag booleans (is_str_key_subscripted, is_nondict_key_subscripted) collapse three distinct states — provably string, provably not string, unknown — into two. "Unknown" is silently merged into "provably not a string," which then means "list."

R5 · Use the runtime facts you already haveVIOLATED

Rule. Where a static type cannot be proven, a cheap runtime check should guard the operation rather than a guess being baked in.

Evidence of violation. The runtime maintains exact kind registries and exposes mojo_is_registered_dict() / mojo_is_registered_list(). These are precisely the functions I called in the debugger to prove the object was a dict — the ground truth was available at runtime all along. Codegen references them in only 11 places, all for repr/formatting in gimple_cpp_core.py. Not one guards a container element access.

Consequence. The program had, at the moment of the fault, everything needed to detect it. mojo_list_get_int received a pointer the runtime knew was a dict, and indexed it anyway.

R6 · A self-hosting compiler must be run, not just emittedVIOLATED

Rule. The Python shim never executes the C it writes, so it cannot fail on a miscompile. Any check that only exercises the shim proves nothing about the compiled path.

Evidence of violation. The shim happily emitted (MojoList *)mojo_dict_new () and exited 0 for months. The defect was only observable by running the self-hosted binary — and even then it was mis-recorded for several sessions as "cosmetic, output is byte-identical," because the verification compared empty stdout captures instead of the real mojo.ci artifact.

Consequence. Green gates on a broken compiler. A compiler that miscompiles itself always looks healthy from the interpreter.

R7 · One chokepoint, not a thousand special casesCORRECT INSTINCT, UNDERBUILT

Worth recording what the design got right. _coerce_to_type carries this docstring:

Works for ANY type pair without function-name awareness.
Scales to 1M functions - ONE routine, not 1M special cases.

That is exactly the right architecture, and it means R2's fix has a home already. The chokepoint exists and is on the path; it is merely total where it should be partial. The remediation below is therefore far smaller than the 239-site number suggests.

How the rules failed, in order

Each rule below, had it held, would have stopped the bug on its own.

#StepRule that would have caught it
1_expr_is_stringish cannot prove _as_str(x) is a string— (a genuine analysis gap; the real defect is what happens next)
2"unprovable" is recorded as is_nondict_key_subscripted = TrueR4
3else: inferred['bindings'] = 'MojoList *' guesses a concrete kindR4, R1
4Call site coerces a real MojoDict * into the declared MojoList *R2
5Coercion emits (MojoList *), silencing GCCR3
6Every bindings[k] lowers to mojo_list_get_intR1
7Runtime indexes a dict as a list; no guard consults the kind registryR5
8Shim exits 0; only the self-hosted binary faultsR6

Eight steps, seven of them structural. The analysis gap at step 1 is ordinary and forgivable — a static analyser will always have blind spots. Everything after it is the design converting a blind spot into 34 GB of wild pointer arithmetic.

Remediation, in leverage order

  1. Make _safe_coerce_emit refuse impossible conversions (R2). One edit, one chokepoint, already on the path. Define a small incompatibility relation — distinct container kinds (MojoList/MojoDict/MojoSet/ MojoBytes) never convert to one another — and raise with both types and the source location. This is the change that turns every future instance of this entire bug class into a build failure with a precise message. Expect fallout: it will surface existing latent miscompiles. That is the point, and they should be fixed, not exempted.
  2. Introduce the missing predicate and route the 239 sites through it (R1). A single container_kind(value_or_type) -> 'list'|'dict'|'set'|'unknown'. Mechanical, reviewable, and it makes a fix like the one I landed a one-line change in an obvious place instead of one line inside a 907-line function.
  3. Represent "unknown" explicitly (R4). Replace the two-boolean key encoding with a three-valued result. An unproven key must select the opaque representation (int64_t box) or a guarded runtime dispatch — never a concrete container kind.
  4. Ban ad-hoc casts (R3). All 146 sites emit via the chokepoint. Enforce with a grep-based test that fails CI on a literal (MojoList *)/(MojoDict *) outside gimple_gen_resolve.py.
  5. Guard unproven container access at runtime (R5). Where the kind is unknown, emit a mojo_is_registered_dict()-guarded dispatch. A branch is cheaper than a multi-session debugging hunt, and the registries already exist.
  6. Add a gate step that runs the self-hosted binary on real work and checks the artifact (R6). Not exit code — artifact size and content. MOJO_NO_SHIM=1 ./mojoc mojo.py --dump-full producing a 0-byte mojo.ci must fail loudly. This one check would have caught the regression the moment it appeared.

What "obvious" should look like

The test for whether this is fixed is not "is the SIGBUS gone." It is: can a reader determine, from one place, how a dict subscript becomes C? Today the honest answer is no — it requires reading 239 decision sites across 12 files and knowing which of them wins. After remediation the answer should be: one predicate decides the kind, one chokepoint converts between kinds and refuses the impossible, and every emission site is downstream of both. At that point a wrong container type is a build error, not a 26-millisecond SIGBUS 34 GB past the end of a slot array.

Status update — 2026-09-13, R3 migration pass

R2/R4/R6/R1(partial) landed earlier the same day (634852c, fe1c36e, b00955c) — see the project memory for that history.

R3 (ban ad-hoc casts): of the 169-cast baseline frozen by test_no_new_container_casts.py at 634852c, 139 sites routed through a real chokepoint this pass, baseline lowered 169 → 30:

  • 62 sites across gimple_gen_infra/calls/exprs/loops/methods/stmts.py now go through gen._coerce_to_type — the GIMPLE-statement R2 chokepoint itself (so these also inherit R2's impossible-conversion refusal, not just cast consolidation).
  • 74 sites in gimple_cpp_core.py (the separate C++ fallback expression-string lowering path — no `gen` statement stream to emit into, so the GIMPLE chokepoint doesn't fit) now go through a new sibling helper, _cpp_as(), added to that file. It is a pure text-consolidation cast (R1: one function, not 74 independent f"(MojoList *)(...)" sites) with deliberately no R2 refusal — every site using it had already proven the value's real kind via a static-type branch before the cast, so this is provably a zero-behavior-change refactor (byte-identical generated C++), not a coercion decision.
  • 3 more sites (a second pass, same day) needed real behavior fixes, not just routing: all()/any() and enumerate() over a statically-known MojoDict */MojoSet * now materialize via mojo_dict_keys/ mojo_set_sorted before the list-based runtime call, instead of reinterpreting the dict/set header as a list. set.update(a_list) got a real per-element mojo_set_add_int/_str loop (the bulk mojo_set_update call only accepts another MojoSet *), and bytes.join(...) got the same dict/set materialization as all()/any().

The remaining 30 are comments the grep also matches, C source text with no gen in scope to route through (raw runtime-helper/struct-allocator strings, already either runtime-guarded or safe-by-construction), or genuine "no static proof, could really be a different container kind at runtime" sites — routing THOSE through the R2-refusing chokepoint would trade a silent miscompile for a build crash on currently-working code. Every one of the 30 now carries an inline comment naming which case it is and, where relevant, what a real fix would need (a runtime mojo_is_registered_dict/_set guard, mostly).

Status update — 2026-09-13, R1/R5 follow-up

Auditing the 30 remaining R3 exceptions surfaced a real R1 violation this same session had just introduced: the "materialize a dict's keys / a set's elements / else coerce to list" shape was independently written out five separate times — in all()/any(), enumerate(), str.join(), bytes.join(), and shlex.join() — as each one got its own R3 fix earlier the same day.

Consolidated into one function, gimple_gen_infra._materialize_as_list(gen, src_type, value), and routed all five call sites through it (R1: "consolidate duplicates... if two files do the same thing, merge them" — applied here to code this very pass had just duplicated). Baseline lowered 30 → 28 as a side effect (the fifth, previously-uncoercible fallback cast in each copy collapsed into one).

With the five call sites sharing one function, the residual "genuinely unknown/boxed handle" branch — DESIGN.html's outstanding R5 gap, previously left undone in all five copies because fixing it meant duplicating a runtime-guard dispatch five times — became a single, one-time fix: _materialize_as_list now guards that case with mojo_is_registered_dict/ mojo_is_registered_set before falling back to list, closing bugs/CODEGEN_all_any_dict_set_miscompile.md for real, for all five call sites at once. set.update(x) was also refactored onto the same helper plus a shared per-element mojo_set_add_int/_str loop, replacing its own remaining R3 exception.

Continued auditing found 4 MORE real, pre-existing sites (not created by this session's own work) that reach a container-kind coercion with a variable source type that can genuinely be MojoDict */MojoSet * in valid Python, not just an ambiguous boxed handle: tuple/list-unpack targets (a, b = some_dict, *a, b = some_dict, [a, b] = some_dict — all real Python, unpacking a dict's keys) and a slice-assign splice RHS (x[:] = some_dict). Confirmed via an actual crash repro (a, b = d raised "cannot coerce MojoDict * to MojoList *" before the fix) — this disproved this session's own earlier reasoning that one of these four (_tuple_elem_value's fallback) could only be reached via an upstream bug. All four routed through _materialize_as_list too.

Continuing the same search (guards that exclude MojoDict */MojoSet * where the real Python builtin accepts any iterable) found 3 more: bytes(a_dict)/ bytearray(a_set) of ints (a valid bytes()/bytearray() source in real Python) previously fell to the wrong branch entirely, silently producing zero-filled bytes of the wrong length rather than crashing; min(a_dict)/max(a_set) (real Python: min/max key or element) fell through to an unsupported stub. Most severe: sum(a_dict)/sum(a_set) had no dispatch anywhere in the path — not even an ad-hoc cast in this codegen — because mojo_sum/ mojo_sum_double themselves unconditionally reinterpret their argument as MojoList * at the C level with zero runtime check. All fixed via _materialize_as_list, which — as a side effect — also adds the R5 runtime guard to sum()'s previously-unprotected boxed/untyped case. 8 real bugs found and fixed this pass, beyond the 5-site duplication this session's own R3 work had created. Checked in/not in membership testing too — already dispatches correctly on dict/set/list, no fix needed there.

A ninth, structurally different bug: gimple_gen_methods.py's boxed-`int64_t` method-name-based unboxing dispatcher resolved .remove() to MojoSet * and .clear() to MojoList * unconditionally — both are real methods on multiple container kinds in Python (.remove() on list AND set; .clear() on list, dict, AND set), so a boxed value that was actually a MojoList * had .remove(x) routed into _lower_set_method, which has no 'remove' case at all, silently no-op'ing instead of removing the element. Fixed with a real mojo_is_registered_dict/_set runtime dispatch (falling back to list) before calling the matching runtime function, mirroring the existing dict-vs-list dispatch pattern already used elsewhere (_gen_for_iter, DelStmt subscript handling). Verified via an isolated compile plus simd.mojo.

R1 full migration (the ~300 originally-scoped independent decision sites, most of which are genuine heuristic inference under real ambiguity rather than mechanical duplication like the case above) and general R5 infrastructure for the remaining unguarded sites are still open — this pass fixed the high-leverage, low-risk instances the R3 work itself created plus 9 genuine pre-existing bugs the same search technique surfaced, not the larger pre-existing scope.

Full gate, run at the end of this batch: check-gimple, check-runner, check-modcache, check-selfhost, check-runtimediff, check-linkmode, check-no-new-casts (28 casts, baseline unchanged), compile_stdlib.py (664/664, 0 failures), and a from- scratch stdlib dylib rebuild (0 skips) all pass. check-noshim-dumpfull fails — the same pre-existing self-host module-drop divergence (byte offset 2390, `gimple_gen_coro` missing from the self-hosted build) confirmed via git stash bisection to exist on the untouched b00955c tree, unrelated to this session's R1/R3/R5 work — see bugs/CODEGEN_noshim_dumpfull_preexisting_divergence.md, tracked separately.

Status update — 2026-09-13, check-noshim-dumpfull root-cause via lldb

Used tools/gdbtool (lldb) directly on the self-hosted mojoc binary to root-cause the pre-existing divergence above, per the "when the writer is in the compiler, instrument the compiler" methodology in HOW-TO-DEBUG.html — with one correction: instrumenting the compiler's OWN SOURCE proved actively dangerous (see below), so the real work was done with lldb breakpoints/backtraces against the already-built binary instead.

Found and fixed 2 real bugs. A conditional breakpoint on mojo_exc_msg_set caught a zip()-nested-tuple ValueError (meant to be caught locally by a try/except and fall back gracefully) escaping to the module-level handler — but only while a COMPILED PYTHON GENERATOR (gimple_gen_stmts._iter_ast / gimple_gen_coro._walk, both yield-based AST-tree walkers used internally by this compiler) was suspended mid-yield on the call stack, confirmed via the backtrace showing __mojo_coro_yield / __mgco__iter_ast_body frames at the exact moment of the raise. A yield function compiles to a REAL stack-switching coroutine in this codegen, and this runtime's own docs already state "a coroutine body can't use setjmp/longjmp directly" — a try block's setjmp captured on the resuming stack, longjmp'd to from code running on the coroutine's own separate fiber stack, is undefined behavior. Neither function's many call sites needed laziness, so both were rewritten as plain iterative list-building functions, eliminating the coroutine machinery for these two internal walks entirely. Verified: the shim-vs-noshim size gap dropped from ~4MB to ~196KB, and gimple_gen_coro is now byte-for-byte present in both builds.

Important lesson, paid for the hard way: adding new debug-tracing code directly into this compiler's own self-hosted source — even a plain, always-disabled bool flag guarding dead-at-runtime print() calls — broke make mojoc's own SHIM-compiled build outright (undefined-struct errors), because this compiler does WHOLE-FUNCTION type unification and new code can shift how OTHER, unrelated variables in the same function get statically typed. All such instrumentation was reverted; further investigation used lldb directly against the built binary instead.

A THIRD, much smaller divergence remains: the myinterpreter module still drops self-hosted, root-caused (via lldb backtrace) to from_base = set() in execute_StructDef being mis-inferred as MojoDict *. Precisely bisected (by truncating a working copy of the real file and re-running --dump-full, ~15s per iteration) to: the mistyping requires the mere PRESENCE, anywhere later in the same class, of a self.<attr>.update(...) call — specifically the method name "update" on a self. attribute, regardless of which attribute or what argument. Root mechanism not yet found despite ruling out several specific candidates (see the bug doc for the full elimination list) — tracked for further work.
