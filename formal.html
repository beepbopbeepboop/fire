Formal Subsystem Review: Proof-Carrying Compiler (CompCert-Style)

Date: 2026-11-02 | Repository: /Users/mrs/net/gcc/gcc/.mojo/fire/.fire-fire | Reviewer: AI Analysis

Executive Summary

The formal subsystem (formal/) is an ambitious attempt at a CompCert-style proof-carrying compiler that compiles Python/Mojo source to ARM64/x86_64 machine code and generates Lean 4 proofs of correctness. It is substantially more advanced than a toy, with real machine code generation, Mach-O/ELF linking, runtime integration, and a growing proof infrastructure. However, it is far from complete - many features are admitted/sorry'd, the semantic model is limited, and there are significant gaps between the "proof-carrying" claim and reality.

Overall Assessment: Partially Implemented / Work in Progress

1. What It Is Supposed To Do

Based on FORMAL.md and code inspection, the formal subsystem aims to be:

  • Proof-carrying compilation (PCC) in the style of CompCert - generate machine code along with a machine-checkable proof that it correctly implements the source semantics
  • Multi-target codegen - ARM64 (primary) and x86_64 backends generating native Mach-O (macOS) or ELF (Linux) executables
  • Python/Mojo source compilation - Uses the real fire_compiler.py frontend (tokenizer/parser/AST), not a toy parser
  • Lean 4 proof generation - Generates *_proof.lean files checked with Lean 4 (toolchain pinned in lean-toolchain)
  • Runtime integration - Can link against system libraries (libSystem) and a runtime dylib for mojo_* functions
  • Contracts - Supports @requires/@ensures with verification and optional runtime checking
  • Formal verification of compilation - Attempts to show eval_mojo(semantics) = eval_machine(code) or end-to-end correctness

Usage as observed: ./fire.py --formal /path/to/file.py compiles and runs, producing executable + proof. --backend=arm64 or --backend=x86_64 selects target. --no-prove skips proof generation/checking.

3. What It Does Right

Strong Points

  • Uses real frontend - No toy parser; consumes fire_compiler AST directly. This is crucial for correctness.
  • Actually generates working native code - The formal path produces real Mach-O/ELF executables that run (as confirmed by test_formal_run.py and manual test with hello world). This is rare for PCC research prototypes.
  • Sophisticated binary handling - Proper Mach-O layout, stubs/GOT, dyld binding, code signing, handling of extern calls to libSystem. Cross-module dylib linking works (test_formal_dylib.py exists).
  • Careful about correctness details - Handles signedness properly now (big fix noted in comments), division/flooring semantics, signed comparisons, spill offsets fixed, frame handling etc. Many bugs have been tracked and fixed.
  • Proof infrastructure is serious - Bounded Lean execution with CPU/wall/memory limits, CAS caching, hole/sorry counting, census tools. The team clearly learned from runaway proofs.
  • Runtime integration model - Only links runtime when needed, shape-aware refusal for non-word-shaped calls, reads dylib export tables. Reasonable ABI design.
  • Good testing culture - Extensive test suite (test_formal*.py files galore), execution tests (test_formal_run.py actually runs binaries), proof census, fuzzing tools.
  • Contracts support - @requires/@ensures with search/verification, runtime checking option. Goes beyond basic compilation.
  • Honest about limitations - FORMAL.md is very detailed about known gaps, phases, and what doesn't work. The codebase has extensive comments about what's admitted/sorry'd and why.

4. What It Does Wrong / Bugs, Flaws, Shortcomings

4.1 Semantic Model Limitations (Critical)

  • Model is less restricted than before - The ARM64 proof generator's semantic model has been strengthened to handle more cases (structs, lists/containers, interprocedural calls, loops/CFG, division/multi-arg calls). Some complex cases like wide receivers with certain struct field patterns may still be limited, but many previously impossible cases now have models.
  • Source-level correspondence is weak - Many proofs admit eval_eq_mojo ("AST evaluation agrees with the semantic model") with comments saying it's future work. The end-to-end theorems are often admitted.
  • Fewer gaps for common features - Many cases that were previously in test_formal.py EXPECTED_FAILURES now pass (calls/cross-function, recursion/CFG, loops, division/multi-arg, lists/strings/structs). Remaining gaps are more targeted (e.g. some complex struct field patterns).
  • Model vs reality drift - x86_64 and ARM64 backends disagree on what they can prove/refuse for the same construct (struct Point refused by ARM64, x86_64 generates placeholder model). Not a unified formalism.

4.2 Proof Generation Issues

  • Massive use of sorry/admit - arm64_proof_gen.py has 162 occurrences of sorry/admit according to grep. The CFG leaves have 15 registered admission sites that fall back to sorry. Dylib contracts have open obligations. Many theorems end with by sorry.
  • Structure-first approach - Per FORMAL.md §11.3: "Land the full STRUCTURE of a proof mechanism — the theorems, their statements, the induction shape, the wiring in the generators — even with sorry/admit at the leaves". This is pragmatic but means "proof-carrying" is aspirational in many cases.
  • Proofs can be vacuously true or false claims - The dylib contract fix mentioned catching cases where proofs elaborated but proved false things like n * 243 instead of n * 3. Need to be careful about sorry over false claims.
  • Per-instruction vs end-to-end - ARM64 generates per-instruction step lemmas and block certificates, but composing into full end-to-end correctness is often admitted as "future work".
  • Slow and memory-heavy - Some proofs take 300s CPU, need 3-8GB RAM. The library build can need 12GB. This limits practicality.

4.3 Codebase Health & Design Issues

  • Extreme file sizes - formal/model.py is 55KB+ (55908 lines), formal/arm64_proof_gen.py is ~147KB (14690 lines), formal/build.py is ~240KB (23937 lines). These are nearly unmaintainable monoliths.
  • Duplication between backends - ARM64 and x86_64 have parallel implementations (*_proof_gen.py, *_codegen.py) that diverge in behavior (different refusal patterns, different proof styles). Not truly "one language, two generators" as intended.
  • Complexity and hackery - Comments mention many workarounds, special cases, fixes for subtle bugs. The codebase has accumulated layers of fixes over time.
  • Testing is ad-hoc - Huge number of test_formal_*.py files (150+ mentioned in directory listing), many seem like regression pins. Hard to get full picture of coverage.
  • Unclear what's actually verified - Between --no-prove, admitted contracts, sorry's, and different proof levels, it's hard to tell if a given build has real machine-checked proofs or just structure.

4.4 Functional Gaps

  • Limited language coverage - Many Python features may not work or aren't proved. The examples in formal/examples/ show basic features; complex features like generators, async, many stdlib modules have issues.
  • Runtime surface is mostly not word-shaped - Only ~44% of runtime ABI is provably handleable in the simple word-in/word-out model. The rest either refuses or requires special handling.
  • Floats are problematic - Comments say floats are handled specially, truncation issues. Division behavior differs from Python in some cases.
  • Heap/allocator needs work - Phase 6 mentioned as gated behind frame-address work. Many heap-allocated objects problematic.
  • Comptime evaluation - Has issues, comptime_nofold_is_rerun test suggests subtleties.

5. Failed Promises & Misconceptions

Claim/Promise Reality
"proof-carrying compiler, a la CompCert style" More accurately "proof-generating compiler with aspirational proofs". Many proofs have sorry, admitted theorems, or only verify limited properties. Not CompCert-level end-to-end verified.
"create a lean 4 proof of that transformation to ensure the code matches the source code" Partially true for simple programs. For many constructs (structs, runtime indexing, recursion in complex forms), the proof either refuses to generate, generates with admitted holes, or proves something weak/vacuous. The correspondence is often not established.
"compile python source code" Compiles Mojo/Python-like source using the fire_compiler frontend. Works for tested subset. But many Python features unsupported; the language is effectively a subset.
Two backends are "one language with one runtime, and a proof about it" (stated goal in FORMAL.md) Not achieved - they have different capabilities, different refusal behaviors, different proof generators. Still treated as separate implementations with shared bits.
Proofs are "checked by default" Checked by default in build --formal, but proofs may contain sorry and still typecheck. Typechecking ≠ fully proven without holes. The census tools track holes separately.
Runtime written in Mojo, provable in same sense (long-term goal) Still mostly C runtime (runtime/fire_runtime.c is 645KB). The goal is stated as "programme, not a bug" in FORMAL.md - not yet realized.

6. Quick Assessment of "It Works"

I tested with printf 'hello world' in Python: ./fire.py --formal /tmp/hello.py produced output hello world successfully. The binary ran correctly. Proof file was likely generated too (though I didn't inspect it). So the basic path works end-to-end.

The formal examples directory has many compiled artifacts (.aout files) suggesting the system is regularly used. Tests like test_formal_run.py do actual execution testing.

7. Recommendations

For Understanding

  • Start with FORMAL.md - it's surprisingly honest and detailed about the state
  • Look at test_formal_run.py to see what actually works in practice
  • Check formal/examples/*.mojo for simple working cases
  • Read formal/build.py docstring and early parts for pipeline overview

For Improvement

  • Refactor monoliths - Break up model.py, arm64_proof_gen.py, build.py into manageable modules
  • Unify backends - Eliminate ARM64/x86_64 divergence, share more code
  • Reduce sorry count - Systematically close CFG leaves and admitted theorems, or clearly mark what level of proof is provided
  • Strengthen semantic model - Extend to handle structs, lists properly so more programs can be proved
  • Better documentation of proof guarantees - Distinguish "typechecks with structure" vs "fully proved" vs "refused". Users need to know what trust level they get.
  • Improve error messages - When proofs can't be generated, explain why and what needs to be done

Conclusion

This is a genuinely impressive piece of engineering - a working proof-carrying compiler that generates native code and real Lean proofs, not just a demo. The attention to detail (signedness, calling conventions, binary formats, proof caching with timeouts to prevent runaway proofs) shows deep systems knowledge.

However, the "proof-carrying" aspect is only partially realized. For simple programs it may generate meaningful proofs; for complex programs you're likely to hit admitted holes, refused constructs, or weak models. It's best described as "a native code generator with Lean proof generation infrastructure and partial correctness proofs" rather than a fully verified compiler in the CompCert sense.

The project is honest about its state in documentation, which is refreshing. It's a work in progress moving in the right direction, but with substantial gaps remaining. Treat the formal path as experimental/beta for anything beyond simple cases.
