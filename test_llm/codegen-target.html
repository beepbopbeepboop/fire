Codegen performance target

What fire.py has to produce, measured against the Metal kernel it is meant to be able to call. Set 2026-09-29.

The workload

One forward step of the model in test_llm/test_llm.py: d_model 128, d_ff 256, 6 layers, bf16 weights, gated linear attention with one d×d state per layer. A "step" is N tokens through all six layers:

q, k, v = W1[0..2] . x
S       = alpha * S + k (x) v
o       = S^T q
x       = x + W1[3] . o
h       = silu(W2[0] . x) * W2[1] . x
x       = W3 . h                 # next layer's input

This is the only workload the target is defined against. It is chosen because it is what the model actually spends its time on, and because it is the shape the fused Metal kernel already computes — so the two are comparable term for term.

The target

Three tiers, in the order they should be attempted. Each is a statement about the compiled program, not about the hand-written C.

TierWhat must happenPer-step budget at N=1000vs. today's pure Python
T1 — compile The forward and backward run through fire.py --jit at all, and produce the same loss and the same sample text as the interpreter. Today this is blocked: the compiler cannot infer the element type of a list built by a comprehension and handed to a method parameter, so g[i] reads as int64. any —
T2 — C-class scalar code One forward step of the compiled program lands within 2× of the naive C loop, i.e. within 300–1200 µs per step. This is the honest bar for a straight scalar lowering with no GPU involved. ≤ 300 µs ≥ 2×
T3 — inner loops to Metal The compiled program recognises the inner loops and issues them through mg_* instead of emitting scalar C, batching a whole step into one dispatch. Measured today at 22.7 µs per step, so the target is the compiled program reaching that same shape. ≤ 45 µs ≥ 250×

What is between us and T3

  1. T1 first. The remaining compiler gap is element-type inference for a list produced by a comprehension and passed to a method parameter. Everything else in the model compiles: the fixed list-repeat, append, float-field, method-call-site, weak-int64 and return-element bugs are done, and the backend suites are green (326 gimple, 6 interporacle, 33 runtime-diff).
  2. A GPU call from generated C. mg_* exists and is correct, but nothing in the compiler lowers a recognised loop shape onto it. That recognition is the actual T3 work: match the loop nest, not the source text.
  3. Weights resident across calls. mg_weights_dirty() exists because the host already caches the bf16 copy; a training step that updates weights in place must invalidate it, or T3 silently trains on stale weights. This is the one place where "it runs" and "it is correct" come apart, so it wants a test of its own.
  4. bf16 storage on the C side. The kernels speak bf16; the host converts. A model that kept its weights in bf16 would halve what crosses the bus again, and test_llm.py already has a tested bf16() to model it on.

The honest caveat

The 26.7× is fused GPU kernel vs unoptimised scalar C. A blocked, vectorised CPU kernel — vDSP, or four double accumulators by hand — would plausibly take 10–50× off the C column, which would put T2 in the same range as T3. Before treating 26.7× as the prize, the C baseline needs to be the best C we can write; otherwise T2 and T3 are being measured against a strawman. The per-step rates (22.7 µs vs 606 µs) are the honest comparison, and even those assume the naive loop.
