Codegen performance target

What fire.py has to produce, measured against the Metal kernel it is meant to be able to call. Set 2026-09-29.

The workload

One forward step of the model in test_llm/test_llm.py: d_model 128, d_ff 256, 6 layers, bf16 weights, gated linear attention with one d×d state per layer. A "step" is N tokens through all six layers:

q, k, v = W1[0..2] . x
S       = alpha * S + k (x) v
o       = S^T q
x       = x + W1[3] . o
h       = silu(W2[0] . x) * W2[1] . x
x       = W3 . h                 # next layer's input

This is the only workload the target is defined against. It is chosen because it is what the model actually spends its time on, and because it is the shape the fused Metal kernel already computes — so the two are comparable term for term.

Both are shown so the difference is visible rather than argued. Agreement is exact (max |diff| = 0) at every step count: split-K is a reassociation of the same sum, and the f32 accumulation order is indistinguishable from the scalar order here, so nothing is being traded away for the speedup. Per-step at N=1000: 14.5 µs GPU against 258 µs blocked C.

Every figure above is the median of three consecutive runs, and the median matters: a single cold run of this benchmark put the CPU baseline at 1327 ms naive / 1031 ms blocked — a 3.7× outlier — which would have read as 70× against blocked C. The GPU columns barely moved across the same runs (14.5 ms every time), so it is the CPU baseline that is sensitive, and a single-sample comparison against it is not a measurement. Take three.

The blocked C column is the honest CPU floor. It is slower than the naive loop at N=1, which is why the table starts at N=1 rather than at the first point GPU wins: at one step the run is almost entirely dispatch and pipeline overhead, and the blocked kernel's tiling has nothing to amortise. The honest statement is that Metal wins from about N=10 and the win grows with the batch — which is the whole reason a fixed per-step cost matters less here than a per-token one.

The target

Three tiers, in the order they should be attempted. Each is a statement about the compiled program, not about the hand-written C.

TierWhat must happenPer-step budget at N=1000vs. today's pure Python
T1 — compile The forward and backward run through fire.py --jit at all, and produce the same loss and the same sample text as the interpreter. Landed. The element-type inference gap this was blocked on is fixed (a parameter passed to a callee whose own parameter is a container is a container, and a weak int64_t type hint now yields to a real lowered type). The forward and backward now run through fire.py --jit and print. Two further gaps are documented rather than papered over — see the bugs/hard/ entries — and the model's parameter count is computed structurally to stay clear of the first of them. any —
T2 — C-class scalar code One forward step of the compiled program lands within 2× of the naive C loop, i.e. within 300–1200 µs per step. This is the honest bar for a straight scalar lowering with no GPU involved. ≤ 300 µs ≥ 2×
T3 — inner loops to Metal The compiled program recognises the inner loops and issues them through mg_* instead of emitting scalar C, batching a whole step into one dispatch. Measured today at 22.7 µs per step, so the target is the compiled program reaching that same shape. ≤ 45 µs ≥ 250×

What is between us and T3

  1. T1 is done — the model compiles, links, runs and prints through fire.py --jit, with the same config, vocab and state numbers as the interpreter. The backend suites are green (330 gimple, 6 interporacle, 33 runtime-diff, 31 model tests). Two documented gaps remain, neither of which blocks T2: cross-function container element types, and a parameter used only as a method receiver (the latter is why the compiled build's parameter count is still wrong; the count is computed structurally to stay clear of it).
  2. A GPU call from generated C. mg_* exists and is correct, but nothing in the compiler lowers a recognised loop shape onto it. That recognition is the actual T3 work: match the loop nest, not the source text.
  3. Weights resident across calls. mg_weights_dirty() exists because the host already caches the bf16 copy; a training step that updates weights in place must invalidate it, or T3 silently trains on stale weights. This is the one place where "it runs" and "it is correct" come apart, so it wants a test of its own.
  4. bf16 storage on the C side. The kernels speak bf16; the host converts. A model that kept its weights in bf16 would halve what crosses the bus again, and test_llm.py already has a tested bf16() to model it on.

The honest caveat

This caveat used to stand unresolved — the old 26.7× was against a scalar C loop, which is a strawman. It is now settled with a measurement rather than an estimate: the blocked C column above is four double accumulators with tiling, and the headline 17.8× is quoted against it. The naive column is kept alongside only so the gap between the two baselines stays visible.
