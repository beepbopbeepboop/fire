Metal backend for the inner loops

Notes and measurements — built 2026-09-29 on an Apple M5 Max. Everything here lives in test_llm/.

What is here

  • kernels.metal — the inner loops as MSL compute kernels (f32, plus native bf16 variants)
  • kernels.metal.inc — generated from the above: the MSL as a C string, so the shipped artifact needs no build-time Metal step
  • metal.h — the C API: mg_* (one dispatch, synchronous) and mg_batch_* (many dispatches, one wait)
  • metal.m — the ObjC host: device / queue / library / pipelines, buffer upload, both APIs, with a scalar C fallback in every entry point
  • bench.c — the benchmark: every kernel, the model's inner loops at real widths, the crossover sweep, and f32 vs bf16
  • test_llm.py — the ~1M-parameter pure-Python model these kernels exist for
clang -fobjc-arc -O2 -I test_llm -framework Foundation -framework Metal \
      -o /tmp/metal_bench test_llm/bench.c test_llm/metal.m -lm
/tmp/metal_bench

-fobjc-arc is load-bearing, and omitting it fails silently. metal.m builds its device, queue, library and pipeline states once in mg_init and keeps them in file-scope statics for the life of the process. Under ARC those statics are strong and retain what is assigned to them. Without ARC they are raw pointers, so every object built inside mg_init's @autoreleasepool is released when that pool drains — while g_ok and g_tried, being plain ints, still report success. The result is not a compile error and not a message: mg_available() returns true and the first dispatch dereferences freed memory, so the benchmark dies with a bare Segmentation fault: 11 and no output at all. If the bench segfaults before printing its first table, check the build flags before suspecting the kernels.

The kernels

mg_axpy, mg_matvec (one threadgroup per output row plus a threadgroup tree reduction), mg_attn_state (16×16 tiles, in place, no temporary), mg_attn_read (o = S^T q), mg_add_scaled. All fp32: MSL has no double type at all — not a hardware limit (Apple Silicon's GPU does fp64), the shading language never exposed it. The ARM C path stays fp64 and is the reference; agreement is ~1e-7 relative, i.e. f32 precision, which is the correct answer for a bf16-weight model.

The -std setting, and what it actually buys

The macos-metal* names top out at 2.4 and are a dead end. The real ones are the generic language versions:

xcrun -sdk macosx metal -std=metal3.2 ...      # 3.0 / 3.1 / 3.2 / 4.0 exist

and for the runtime-compiled path, the same thing as an option:

MTLCompileOptions *o = [[MTLCompileOptions alloc] init];
o.languageVersion = MTLLanguageVersion3_2;      // what metal.m does
id<MTLLibrary> lib = [dev newLibraryWithSource:src options:o error:&err];
VersionsEffect
2.4 → 3.2Native bfloat: bf16 buffers, arithmetic and rounding in the GPU. Below 3.2 you get unknown type name 'bfloat'.
any versiondouble is never available. Rejected identically at 2.4, 3.0, 4.0 and 4.1. MSL has no double at all; this is the language, not a setting.
4.1Not selectable — the enum's max is MTLLanguageVersion4_1 but the compiler's is metal4.0, and there is no metal5 or MTL5 in this SDK. system_profiler reports Metal 4.

The Metal 4 API (MTL4CommandQueue, argument tables — the low-overhead dispatch path that would fix the round trip measured below) is reachable at runtime: [dev newMTL4CommandQueue] exists and returns a live queue, and -[MTL4CommandQueue commandAllocator] answers respondsToSelector:. Neither is declared in this SDK's public protocols, so building on it means reverse-engineering the surface.

f32 vs native bf16, measured

bf16 is the model's real precision, so this is the case that matters.

2.1e-3 relative is exactly bf16 precision (8 mantissa bits) and is the correct answer for a bf16-weight model — the Metal result is not "less accurate", it is as accurate as the numbers it is multiplying. The gain grows with size because bf16 halves what crosses the bus.

MSL facts that cost real time

  • Thread indices come from [[thread_position_in_grid]] / [[threadgroup_position_in_grid]] / [[thread_position_in_threadgroup]]. Declaring an extra constant unsigned int &gid parameter compiles clean and binds it to whatever the next buffer index is: every thread then computes with gid == 0 and only element 0 is written.
  • A scalar kernel argument is constant T &name (by reference) or bare — not constant T name. And uint is a vector type, so scalars are unsigned int.
  • This SDK only has newBufferWithBytesNoCopy:length:options:deallocator: (a nil deallocator is the no-copy form) and newComputePipelineStateWithFunction:error: — there is no …WithFunctionName:error: and no MTLComputePipelineDescriptor.
  • [queue commandBuffer] returns a command buffer; the encoder comes from [cb computeCommandEncoder]. Calling setComputePipelineState: on the command buffer throws at runtime.
  • Never hand an f64 buffer to an f32 kernel zero-copy: it reinterprets the mantissa halves, writes plausible-looking numbers, and is completely wrong. Convert at the boundary.

Measurements

The dominant fact, and it decides everything else:

bare no-op kernel, commit only        12.3 us/call
bare no-op kernel, commit + wait     173.3 us/call

A Metal round trip here costs ~173 µs. The model's inner loops are 16K MACs — a few µs of arithmetic. So per-loop dispatch can never win; the whole question is how much work a dispatch has to carry.

Metal approaches but never passes a naive C triple loop — and the ARM column is an unoptimised -O2 scalar loop, so a blocked/vectorised C kernel would only widen the gap. A 173 µs wait against kernels of this size is the signature of a virtualised GPU, so the honest reading is that these numbers characterise this environment, not Metal on an M5 Max.

One forward step of the real model

seq_len 24, d_model 128, d_ff 256, 6 layers; the inner loops are exactly the model's, the surrounding bookkeeping (residuals, norms, softmax, optimizer) stays in ARM C. 20 steps:

pathms/step
ARM C, every inner loop in C8.44reference
Metal, one dispatch+wait per loop255.90.03×
Metal, batched into one submission18.40.44×

All three produce an identical checksum to f32. Batching is worth 5.6× over per-loop dispatch, and the operand cache inside a batch (the same weight matrix is handed to the same kernel once per token; re-uploading it each time was 100 MB of malloc+copy per step) is worth another 2.9×. What remains is entirely dispatch overhead: 1620 dispatches × 12 µs ≈ the whole 18 ms.

Verdict

The split works and is correct — ARM keeps all control flow and issues the inner loops, the GPU does the arithmetic, and the result is verified against fp64. The performance verdict on this machine is no: at transformer-layer widths a 173 µs round trip cannot be amortised, and even at 4096×4096 the GPU only reaches 0.62× of a naive C loop.

What would change the answer

  1. One dispatch per step, not per loop. A persistent/fused kernel that loops over tokens and layers internally turns 1620 dispatches into 1 — ~12 µs of overhead against ~7M MACs of work. This is the only change that makes the current arithmetic worth a GPU, and it is the design the mg_batch API is shaped for.
  2. Resident weights across steps, not just within one: the cache is per-batch today, so a model-level cache would remove the 64 KB/token re-upload of W entirely.
  3. A better C baseline. The ARM column is a scalar triple loop. Any honest claim about the GPU needs the CPU side blocked and vectorised first — with vDSP or OpenMP the crossover moves right, not left.
  4. bf16 end to end. The hardware has bf16 and Metal 3.2 exposes it; the C side is still fp64, so every operand pays a conversion. A bf16 model that keeps its weights in bf16 on the CPU side would halve the transfer again — and test_llm.py already has a tested bf16() to model that on.
