HOW-TO-DEBUG

Hard-bug methodology for this compiler, and the worked example that produced it.
Written 2026-09-13 from the match_pattern dict-as-list type-confusion hunt.

The one rule that matters most: a bug that "shimmers" — appears and disappears — is usually being measured wrong, not behaving randomly. Before chasing non-determinism, prove your measurement is sound. In the worked example below, three sessions believed the compiler produced "byte-identical output with only a bad exit code." It actually produced no output at all; the verification had been diffing two empty files for hours.

0. Validate the measurement before you validate the bug

The very first thing to establish is that the thing you are measuring is the thing you care about. Cheap checks that catch most false signals:

  • Check artifact size and mtime, not just exit code or a diff count. diff a b | wc -l returns 0 for two empty files.
  • Time the run. If a job that should take 100 s finishes in 26 ms, it did not do the work. Wall-clock is the cheapest correctness signal you have.
  • Know where output actually goes. --dump-full writes ./mojo.ci; redirecting stdout captures nothing. A stale mojo.ci from an earlier good run will happily impersonate fresh output.
  • Delete the artifact before every run so "file exists" cannot be inherited from a previous run.

1. Establish the hit rate, with an interval

Run the bare reproduction in a loop and histogram the exit codes. Do this before attaching a debugger — debuggers change timing, heap layout and signal delivery, any of which can make a real bug shimmer. 

for i in $(seq 1 200); do
  MOJO_NO_SHIM=1 ./mojoc fire.py --dump-full >/dev/null 2>&1
  echo $?
done | sort | uniq -c

Report it as a confidence interval, not a vibe. For x failures in n trials with x = n, the one-sided Clopper–Pearson lower bound is alpha^(1/n):

observed95% lower bound on p99% lower bound on p
200/20098.51%97.72%
1000/100099.70%99.54%

Sampling alone can never prove 100%. To actually claim 100% you need a structural argument — see §6. Sampling tells you whether to look for a race; structure tells you the answer.

2. Freeze the address space

Data-address breakpoints and watchpoints are worthless if addresses move. Turn off randomization first. 

gdbtool "settings set target.disable-aslr true"
gdbtool "settings set target.env-vars MOJO_NO_SHIM=1"
gdbtool "settings set auto-confirm true"   # else 're-run?' prompts wedge the pty
gdbtool "run fire.py --dump-full"

Then re-run several times and diff the fault data. Distinguish the three cases:

what variesmeaning
nothing at allfully deterministic computation
only the high bits of heap pointersallocator base moves; offsets deterministic — still a deterministic bug
faulting offset / which line faultsgenuine non-determinism: suspect uninitialised memory, a race, or iteration over a pointer-ordered set

3. Identify the wrong datum before hunting the writer

Do not set a watchpoint until you can name the bad value. At the fault, ask the program itself what it thinks the object is — the runtime usually has predicates you can call from the debugger, and calling them is far stronger evidence than eyeballing a struct: 

p mojo_is_registered_dict((long)0xbe24719c0)   # -> 1   it IS a dict
p mojo_is_registered_list((long)0xbe24719c0)   # -> 0   it is NOT a list
p (char*)4296832280                            # -> "key"  the 'index' is a string

Calling a live predicate beats reading raw memory: it answers in the program's own terms and cannot be misread by you.

Confirm the mechanism arithmetically

A hypothesis is only proven when it predicts the exact faulting address. Compute it and compare bit-for-bit: 

p/x (long)(*(long*)0xbe24719c0) + 8*4296832280
#   slots               + 8 * (int64_t)"key"
# => 0x13e32951c0   ==   actual EXC_BAD_ACCESS address 0x13e32951c0

An exact match converts "probably type confusion" into "type confusion, demonstrated." If the prediction is off, your model is wrong — fix the model, not the prediction.

4. Watchpoints: gate them, don't drown in them

A watchpoint on a hot address fires thousands of times. Techniques, cheapest first:

  1. Condition the watchpoint: watchpoint modify -c '(condition)'.
  2. Gate with a breakpoint: set a breakpoint at the function that begins the interesting window whose command list enables the watchpoint, and another at the exit that disables it. This is the single most effective trick for a value written constantly but only wrong once. 
    b interesting_window_start
breakpoint command add 1
watchpoint enable 1
continue
DONE
b interesting_window_end
breakpoint command add 2
watchpoint disable 1
continue
DONE
  3. Count instead of stopping: let it run to completion, read breakpoint list hit counts, then use breakpoint modify -i N-1 to skip straight to the interesting hit.
  4. Prefer -c over auto-continue loops. Repeated breakpoint command add ... continue hit 100+ times has crashed lldb itself in this project (internal LLDB assertion, not a target crash).

Know when a watchpoint is the wrong tool

Watchpoints find who wrote this memory. They are useless when the bad value was never "written" at runtime at all — when it was compiled in. If the faulting instruction is reached on a straight-line path with no preceding store to the operand, stop hunting memory and go read the generated code. In the worked example the "wrong data" was a type decision made by the compiler minutes earlier, in a different process.

5. Read the generated code; ask if it is valid

For a compiler, the emitted .ci/asm is evidence you can read directly, and it is often faster than any dynamic technique. The defect was plainly visible: 

MojoDict * _t6;
MojoList * bindings;              /* <- declared LIST */
  _t6 = mojo_dict_new ();         /* <- allocates a DICT */
  _t10 = (MojoList *)_t6;         /* <- hard cast dict->list */
  _t7 = match_pattern_c16e51 (_t2, _t9, _t10);

Is the codegen valid? No. Specifically:

  • The allocation site produces MojoDict *; the callee's parameter is MojoList *. The two structs are not layout-compatible: MojoList{data,len,cap} vs MojoDict{slots,used,cap,next_seq}. Aliasing maps slots→data, used→len.
  • Every subscript lowers to mojo_list_get_int/mojo_list_set_int, which compute data[i] with i = the key's char pointer (~4.3e9), i.e. slots + 34 GB.
  • The explicit (MojoList *) cast is what makes this invisible to GCC — the cast silences the very diagnostic that would have caught it. The C is well-formed and warning-free; it is semantically wrong.

Note the asymmetry that hid this for so long: the Python "shim" never executes the emitted C, so it happily writes a broken program and exits 0. Only the self-hosted binary — which is that emitted C — crashes. A compiler that miscompiles itself will always look healthy from the interpreter.

6. Proving 100%, structurally

Once the mechanism is known, determinism can be argued rather than sampled:

  • The faulting call is on an unconditional path for that statement.
  • The index is a static string-literal address — identical in every run (confirmed: i = 4296832280 in 4/4 ASLR-disabled runs).
  • The offset 8 × 0x1001c7518 ≈ 34 GB is never mapped, for any heap base.

So p = 1 by construction; the 200/200 sample is consistent with it, and the observed variation is confined to the malloc-zone base (low 32 bits of the dict pointer were identical, 0x4719c0, in every run).

Run under the interpreter/shimbug is in shared logicbug is in the compiled path only

The PC-shift test has a second payoff: once you know the bug is layout-insensitive, you may freely add printf/instrumentation to unrelated functions without fear of perturbing it away.

8. When the writer is in the compiler, instrument the compiler

The compile-time analogue of a watchpoint is a wrapper that traps the moment a value is decided, and prints a stack. Because the shim is plain CPython, this is exact, fast and fully deterministic: 

import gimple_gen_infra as ginf
orig = ginf._infer_param_types
def patched(gen, func, owner_struct=None):
    r = orig(gen, func, owner_struct)
    if getattr(func, 'name', None) == 'match_pattern':
        print(r, file=sys.stderr)
        if r.get('bindings') == 'MojoList *':
            traceback.print_stack()          # <- the 'writer'
    return r
ginf._infer_param_types = patched

Two force-multipliers here:

  • Shrink the repro first. The full closure takes 106 s; compiling the single offending module reproduced the identical bad signature in 0.5 s. A 200× faster loop is worth ten minutes of setup.
  • Copy the tree to a sandbox (/tmp/…) and instrument the copy, so the repo stays clean and you can hack freely.

9. Worked example — the full chain

SIGBUS200/200type confusion gimple_gen_infra.py

  1. Symptom. MOJO_NO_SHIM=1 ./mojoc fire.py --dump-full → SIGBUS in 26 ms, no output. Previously mis-recorded as "byte-identical output, cosmetic exit code" because stdout (empty) was being diffed.
  2. Fault. mojo_list_get_int(l=0xbe24719c0, i=4296832280) from _rewrite_assign_stmt (ast_rewriter.py:691) — the one os.environ['PATH'] = … at fire.py:27.
  3. Wrong datum. l is a registered dict; i is the string "key". Predicted fault address matched actual exactly.
  4. Static cause. The emitted C declares MojoList * match_pattern_c16e51(…, MojoList * bindings) and passes (MojoList *)mojo_dict_new ().
  5. Writer. gimple_module_gen.py:4023 → _infer_param_types → gimple_gen_infra.py:2139 else: inferred[pname] = 'MojoList *'.
  6. Root cause. analyze_param_usage reported is_str_key_subscripted=False, is_nondict_key_subscripted=True. Instrumenting the flag-setting line named the four offending keys: bindings[_vn] ×2 (where _vn = _as_str(pat.name)) and bindings[_as_str(…)] ×2. _expr_is_stringish accepted only a string literal, an f-string, or a local bound directly to a literal — so a -> str call result was "not provably a string", and the else branch read absence-of-evidence as evidence-of-list.
  7. Fix. Teach _expr_is_stringish that a call whose resolved return type is char * is a string (gen.func_return_types — real type resolution, not a name whitelist), and record x = <stringish> into str_vars. Inference then yields {'bindings': 'MojoDict *'}.

10. gdbtool gotchas (hard-won)

  • b -a <addr> set before the process exists resolves against an unloaded PIE image and silently never fires. process launch --stop-at-entry first, then set it.
  • b -n <mangled> often fails even when nm shows the symbol (leading-underscore convention; static t symbols). b file.py:LINE via the emitted #line directives is far more reliable.
  • breakpoint command add with several -o flags keeps only the last. Use the multi-line form terminated by DONE, sent as one call.
  • Calling a static C helper from expr needs an explicit function-pointer cast when there is no debug info.
  • At a bare function-entry breakpoint the prologue has not run: read arguments from $x0…, not from frame-relative stack slots.
  • An interactive prompt ("re-run? [Y/n]") wedges the persistent pty and every later command returns nothing. Set auto-confirm true early; if wedged, send a bare Y.
  • This runtime's mojo_print emits no separators between rapid identical calls, so a burst renders as one giant line that defeats grep/tail. Redirect lldb to a file and parse it with Python instead.

11. Checklist

  1. Prove the measurement (size, mtime, wall-clock), delete artifacts first.
  2. Hit rate over ≥200 bare runs; report a Clopper–Pearson bound.
  3. Disable ASLR; confirm which parts of the fault are stable.
  4. Name the wrong datum; interrogate it with the runtime's own predicates.
  5. Predict the faulting address arithmetically; require a bit-exact match.
  6. Read the generated code. Decide explicitly: is it valid, and why not?
  7. If compiled-in, instrument the compiler; if runtime, use gated watchpoints.
  8. Shrink the repro before iterating.
  9. Fix the root cause, then re-run the full gate — a type-inference change has whole-program blast radius.
