Metal GPU Offload on macOS (Future Work)

Status: design note / parking lot. Not implemented. Captured now so we don't lose the plan; we build it down the road once the CPU path (stdlib → MLIR → GIMPLE → C) is solid.

What is built and measured

A dumb Mojo triple loop now offloads itself, bit-exactly, with no annotation and no change to the source:

def gemm_dumb(A: List[Float32], B: List[Float32], C: List[Float32],
            m: Int, k: Int, n: Int):
    for i in range(m):
        for j in range(n):
            acc: Float32 = 0.0
            for p in range(k):
                acc = acc + A[i * k + p] * B[p * n + j]
            C[i * n + j] = acc

Two synthesis paths recognise that exact shape (every clause checked against the AST, not assumed): a one-thread-per-output-element kernel, and a tensor-core kernel. Plus: a per-buffer element-count ABI, a per-kernel grid override, a pipeline-state cache, and a writability mask that stops the runtime copying read-only buffers back.

Peak performance, and how to get it

The single most important fact on this page: arithmetic intensity, not the instruction, decides whether a tensor-core kernel is fast. The same simdgroup_multiply_accumulate, the same fragment layout, the same kernel — differing only in tile size — spans two orders of magnitude.

For a tile R×N stepping K 8 at a time, the arithmetic intensity is RN / (2(R+N)) FLOP per byte — because it loads 8R A-elements and 8N B-elements (that is 32(R+N) bytes) to do 16·R·N FLOP. It depends on neither K nor the problem size, which is what makes it predictable:

MappingLoads per k-stepBytesFLOPIntensityMeasured
1 simdgroup per 8×8 tile64 A + 64 B5121 0242 FLOP/byte0.134 TFLOPS — no faster than scalar
1 simdgroup per 32×32 tile (4×4 grid of 8×8 MMAs)256 A + 256 B2 04816 3848 FLOP/byte0.58 TFLOPS
staged 64×64 (measured slower)512 A + 512 B4 09665 53616 FLOP/byte2–4% slower

At 2 FLOP/byte the kernel is deeply memory-bound, so the MMA is never the thing being waited on and replacing the scalar FMA with it buys exactly nothing. The 8×8 version was built first, verified bit-exact, and measured as a null speedup — the tile size was the entire difference and it was invisible in the code.

The model predicts the measurement. Going 8×8 → 32×32 raises intensity 4.0× and measured throughput 4.3× (0.134 → 0.58 TFLOPS). That is the main reason to trust the cost model below rather than treating these as anecdotes.

Note the honest ceiling this implies: even 64×64 is 16 FLOP/byte, still memory-bound on any GPU whose balance is 50–100 FLOP/byte. Reaching the 117 TFLOPS ceiling needs blocking/reuse across the whole k-loop, not a bigger tile. On a single pass, intensity is capped by RN/(2(R+N)) ≈ R/2 for R=N, so it only grows linearly with register pressure — the two fight each other, and that tension is the real optimisation problem.

The configuration that reaches peak

  • 32×32 output tile, as a 4×4 grid of 8×8 MMAs. This is the reuse: 16 accumulators means each loaded element is used 16 times instead of once, and intensity goes 2 → 8 FLOP/byte. 32×32 is the sweet spot given the no-staging constraint — 64×64 reaches 16 FLOP/byte but measured slower.

  • One simdgroup, not four. 16 accumulators is already 32 registers of acc; four simdgroups of them want 128 registers before any operands, which is the register-pressure cliff. The reuse comes from the tile, not the simdgroup count, so there is nothing to buy by widening it.

  • No threadgroup staging. The staged, double-buffered 64×64 version measured 2–4% slower. Staging would be code that exists to be slower.

  • Fragments read straight from global memory into registers — no smem round trip at all.

  • Out-of-range reads are 0.0, not predicated, because a zeroed A or B row contributes nothing to the product, so the stores are the only place bounds are checked.

The 8×8 fragment layout

A constant of the architecture, not of the matrix. Getting one term wrong transposes the result silently. Lane q holds row (q/4 & 4) + (q/2 % 4), its first value in column (q/4 & 2) * 2 + (q%2) * 2 and its second in the column after:

int fr   = ((lane / 4) & 4) + ((lane / 2) % 4);
int fcol = ((lane / 4) & 2) * 2 + (lane % 2) * 2;
simdgroup_matrix<float, 8, 8> acc;
reinterpret_cast<thread float2&>(acc.thread_elements()) = float2(0.0f);

Verified two ways: an exhaustive 32-lane probe with distinguishable values (test_llm/frag_layout_probe.m), and end-to-end bit-exactness against a naive triple loop.

The cost model a scheduler needs

Two independent costs, and on this machine the first one usually dominates:

T_gpu  =  T_marshal + T_kernel

T_marshal = (bytes_in + bytes_out) / BW_effective
            bytes_in  = sizeof(A) + sizeof(B)          # every buffer uploaded
            bytes_out = sizeof(C)                      # writable buffers only

T_kernel  = 2*m*k*n / TFLOPS_achieved

The decision is T_gpu < T_cpu, where T_cpu for this Mojo List-indexed path measures about 2.0 GFLOP/s. The same GEMM in C runs at 440 GFLOP/s, so the Mojo CPU path is roughly 220× slower than C at the same operation. That gap is why every speedup claim here has to name its baseline: "44× vs the Mojo CPU path" and "~1.3× vs C" are both true of the same run, and only the second is a statement about the hardware.

So the synthesised naive-parallel kernel's compute is already within ~15% of the hand-written Metal kernel (~0.5 ms implied vs 0.436 ms measured). The entire 7× gap is the host round trip moving A, B and C per call — a property of the calling convention, not of the kernel.

Bandwidth roughly doubles with buffer size, which implies a fixed per-call component. A two-term fit needs three points: two points fit two parameters exactly and prove nothing. Also note ms/iter is integer division, so the 32×32×32 "0 ms" floor cannot resolve a sub-millisecond fixed cost — do not read it as zero.

And the tensor core is slower at both shapes (4 vs 3, 10 vs 8). At these sizes both kernels are memory-bound, so the MMA's advantage — which is in FLOPs — is not the binding constraint, exactly as the intensity ladder predicts. A tensor core cannot pay for itself through a calling convention that round-trips every buffer through the host, at any tile size. That is a statement about the marshalling, not about the intrinsic.

Marshalling: the cost that hides everything

Measured, holding FLOPs fixed and stretching k — time tracks bytes, not arithmetic:

Bytes went up 5.66×, FLOPs 8×, time 6.3× — the time follows the bytes. Effective bandwidth through the offload path is about 0.9–1.0 GB/s. Every millisecond spent tuning the kernel was, at these sizes, measuring the marshalling path instead.

The tell is that two completely different kernels — a scalar FMA loop and an MMA kernel — land on the same time. When the work per call changes by 8× and the time does not move, the time is not in the kernel.

What was fixed, in order of size

  1. Cache the pipeline state per kernel name. It was being rebuilt on every dispatch — the driver compiles and validates the function each time. This was the entire fixed per-call floor, invisible in the obvious way: a 32×32×32 GEMM, which should cost nothing, took 1 ms. Fixing it took the floor to 0 ms and 1024×1024×1024 from 10 ms to 7 ms.

  2. Stop copying back read-only buffers. The runtime copied every buffer back, including A and B, which the kernel only reads — 16 of the 17 MB moved per call, device to host and then discarded. 1024×1024×1024: 12 → 9 ms.

  3. Per-buffer element counts. One count for the whole call could not describe three buffers of different lengths.

Still open, and the next thing to attack: newBufferWithBytes allocates fresh per buffer per call (~8 MB twice per call at 512×512×4096). That is the remaining ~10× gap to memcpy bandwidth. Reusing buffers across calls is the obvious fix and is not yet done.

Grid and launch ABI

  • The grid is 1-D. tg = ngroups > 0 ? ngroups : ceil(max(sizes)/tptg) and use = nthreads > 0 ? nthreads : tptg. The launch path sizes the grid from the largest buffer's element count, which silently encodes the assumption one thread per output element.

  • That assumption breaks for tensor cores, where 32 lanes cooperate on one 8×8 tile: an m×n grid would be ~32× too many threads with 31 of every 32 exiting immediately. Both values were already overridable in the runtime, so a per-kernel grid spec cost no ABI change — only a way for a kernel to ask.

  • Grids in use: naive GEMM 0,0 (inferred); tensor-core GEMM 32, ((m+31)/32)*((n+31)/32).

Verifying a GEMM is bit-exact

Reduction order must not be able to hide an error. Fill the data with multiples of 1/16: every partial sum is then exactly representable in f32, so a different accumulation order is the only thing that could produce a difference, and a correct kernel has none.

How to get performance: the checklist

  1. Tile for arithmetic intensity first — RN/(2(R+N)), which predicts throughput. 32×32 is the measured optimum without staging; an 8×8 tile is a scalar kernel with extra steps.
  2. Count per-dispatch fixed costs and cache them. A fixed cost that does not shrink with the work is per-call setup by definition.
  3. Measure bytes moved per call, not just FLOPs. On this machine the two are independent, and bytes usually win.
  4. Copy back only what was written, and take that claim from the type.
  5. Do not stage through threadgroup memory until measured. It was slower.
  6. Compare against both the Mojo CPU path (what a user gets) and optimised C (what the hardware is doing). Only one is a hardware claim.

Open work, in the order I would do it

  1. Reuse device buffers across calls — the remaining ~10× to memcpy bandwidth, and it gates every large-shape win.

  2. Build a real cost model from the tables above and drive the MOJO_OFFLOAD_MIN_ELEMENTS guard from predicted T_gpu < T_cpu rather than a flat element count. The guard should weigh bytes, not elements: the two are independent on this machine.

  3. Widen the recogniser: reductions (with MLX's float4 accumulators, simd_sum, two-level simdgroup/threadgroup reduction as the model), elementwise, transpose.

  4. Decide the tensor-core default on evidence. It is currently off because it measures the same as the naive kernel and is a raw MSL string; that should flip once marshalling stops dominating.

Original plan (2026-09-30, before any of this existed)

The idea in one line

On a Mac we already have a full GPU toolchain in the box: identify the Mojo kernels we want to offload, lower their inner bodies to Metal Shading Language (MSL) / LLVM Metal IR, run them through Apple's IR→binary compiler to get a real .metallib for this machine, and call that from the C we already emit. Result: actual GPU offload on macOS with no external runtime.

Why this is tractable here

Apple ships every layer we need:

  • Metal Shading Language (MSL) — a C++14-based kernel language. Our GPU kernels can be emitted as MSL the same way we emit GIMPLE C for the host.

  • LLVM-based Metal IR (AIR) — Metal compiles through an LLVM IR dialect ("Apple IR" / AIR). Since we already live in LLVM/MLIR land conceptually, we can route kernel bodies into this IR instead of (or alongside) MSL text.

  • metal / metallib compilers — Apple's offline toolchain turns MSL/AIR into a .metallib binary glob targeted at the host GPU. That's the "IR → binary for your machine" piece the user noted.

  • Metal runtime (C API via Metal/Metal.h) — load the .metallib, build a pipeline state, bind buffers, dispatch the grid, read results back. All callable from the C we generate, so the host side is just normal extern calls.

Pipeline (host + device split)

   Mojo source
       │
       ▼
  identify kernels   ──►  inner kernel bodies            host glue stays on CPU
  (offload targets)        │                              │

                  "metalize": lower to            GIMPLE C  (already done)

                           ▼                          │  Metal host wrapper
                   xcrun metal / metallib             │

                     foo.metallib  ◄──────────  dispatch, copy back
                  (binary for THIS Mac's GPU)

  1. Kernel identification. Mark/detect the functions to offload (e.g. a @gpu/kernel attribute, or analysis of for-over-grid patterns). Everything else stays on the CPU path we already have.

  2. Metalize the inner stuff. Lower the kernel body to MSL (text) or to LLVM Metal IR (AIR). This reuses the same lowering discipline as mlir.py / gimple_codegen.py — just a different backend target for the device region.

  3. Router across into LLVM land → binary. Hand the MSL/AIR to Apple's offline compiler (xcrun -sdk macosx metal … → .air → xcrun metallib … → .metallib). Out comes a real binary for this machine's GPU.

  4. Call it from C. Emit a small host wrapper (Objective-C/C using Metal/Metal.h) that loads the .metallib, creates the compute pipeline, marshals arguments into MTLBuffers, dispatches, and copies results back. The generated GIMPLE C reaches it through the same external_call mechanism we just built — so from the program's perspective, the kernel is "just a call." Voilà: offload on a Mac.

What we already have that feeds this

  • external_call lowering — the host→device handoff is just calls into the Metal host wrapper; no new calling machinery needed.

  • mlir.py (table-driven) — the discipline for replaying MLIR ops as a concrete backend is exactly what a "lower kernel body to MSL/AIR" pass needs; the device target is another table of op → emission rules.

  • Two-target codegen shape — host code already goes Mojo → C; device code becomes Mojo → MSL/AIR as a parallel lowering, split at the kernel boundary.

Open questions (for when we pick this up)

  • Kernel marking: explicit attribute vs. inferred from grid/for patterns.

  • Emit MSL text (simpler, lean on xcrun metal) vs. AIR/LLVM IR directly (tighter, but needs the AIR dialect details).

  • Argument marshaling/ABI: how Mojo buffers/Spans map to MTLBuffer bindings and threadgroup sizing.

  • Host wrapper language: Objective-C (Metal/Metal.h) vs. the C++ metal-cpp headers; pick whichever links cleanly from our emitted C.

  • Build wiring: invoking xcrun metal/metallib from the build and embedding or shipping the resulting .metallib.

Upstream alignment

The real stdlib already carries Apple-GPU paths (is_apple_gpu(), _metal_print_write, the print Metal branch in std/io/io.mojo). When the CPU walk-into-stdlib is mature, those branches are the natural seams to light up the Metal target rather than inventing our own kernel surface.
