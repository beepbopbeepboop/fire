Architecture — the self-hosting Mojo compiler

This doc captures the architecture as discovered through the self-hosting bootstrap effort. It focuses on the two-path compilation model and the subprocess shim — the bridge that lets the compiled self-hosted binary delegate to real Python while the true native backend is being hardened.

1. Overview

A Mojo compiler written in Python, bootstrapped to a native binary via GCC -fgimple. The end goal: build/mojo (the compiled binary) runs its own compiled compiler for everything — no Python subprocess at runtime.

2. Two execution paths

Path A — Python-driven (interpreted)

python3 mojo.py <file>.mojo

  1. Reads source; tokenises via py_tokenize; parses via Parser; rewrites via ast_rewriter.rewrite.
  2. Calls gimple_codegen.compile_to_gimple*() in-process (no subprocess for codegen).
  3. Writes .ci (C + __GIMPLE annotations); shells out to gcc -fgimple to compile, then links with runtime/mojo_runtime.c.

The interpreter path (mojo.py run / interpret_and_execute) uses myinterpreter.py directly, bypassing compilation entirely.

Path B — Self-hosted (compiled)

build/mojo <file>.mojo

build/mojo is the compiled transitive closure of mojo.py — it contains compiled versions of mojo_compiler.py, gimple_codegen.py, module_loader.py, etc. When it compiles code, every call to gimple_codegen.compile_to_gimple[_cached](...) is intercepted at lowering time and replaced by the C runtime shim (§4). The compiled binary therefore never runs its own compiled codegen for .ci generation — it shells out to real Python.

Why this matters: .ci output from the compiled binary is real Python's, not the compiled compiler's. Bug fidelity for the self-hosted backend has never been tested for .ci. Only the .tok / .ast diagnostic dumps call compiled Parser / py_tokenize directly — and those historically exposed many bugs (doc/IMPL.md:302-309).

4. The subprocess shim

This is the bridge between the self-hosted compiled binary and the real Python compiler. It's the single most important mechanism in the bootstrap story, and the primary bug surface for "compiling code" via the self-hosted binary.

4.1 Lowering

gimple_codegen.py, lines 9175-9218. When GimpleGen encounters a call to gimple_codegen.compile_to_gimple or gimple_codegen.compile_to_gimple_cached from outside that module (e.g. mojo.py's --dump handler), it replaces the entire call with a single C function call:

gimple_codegen_compile_to_gimple(src, do_imports, filename)

Keyword arguments are supported: the lowering reads node.kwargs to extract do_imports and filename. Positional args win if present. The shim's forward declaration lives at line 25371; its symbol is registered in the externs list at line 16935.

Why interception exists: the compiled gimple_codegen.compile_to_gimple function body is enormous (~10k lines of compiled Python AST-walking and C-generation). Running it natively in the compiled binary is the frontier; the shim is the current workaround.

4.2 The C shim

runtime/mojo_runtime.c, lines 2296-2377:

char *gimple_codegen_compile_to_gimple(char *src, int do_imports, char *filename) {
    // 1. Write source to temp file: /tmp/_mojo_src_<pid>.mojo
    // 2. popen("PYTHONPATH='<MOJO_HOME|.>' python3 -c \"import gimple_codegen; ...\" 2>/dev/null")
    // 3. Read ALL stdout into a static growing buffer
    // 4. If (n > 64 && rc == 0): return the buffer
    // 5. Else: return a silent do-nothing stub
}

The Python one-liner inside the shim:

PYTHONPATH='<mojo_home>' python3 -c "
import sys; import gimple_codegen;
src = open('/tmp/_mojo_src_<pid>.mojo').read();
print(gimple_codegen.compile_to_gimple(src, <do_imports>, '<filename>'), end='')
" 2>/dev/null

4.3 Known bugs in the shim

1. Silent error masking (2>/dev/null + stub fallback)
Every Python traceback is sent to /dev/null. On any failure (Python exception, import error, syntax error), the shim returns a do-nothing C stub. The compiled binary writes this stub as the .ci — it compiles and links, but the program does nothing. Errors are invisible: build/mojo --dump bad.mojo silently succeeds with a stub.

2. if (n > 64 && rc == 0) threshold
A valid output ≤64 bytes is treated as failure → stub. In practice, generated C is 20-54KB (the preamble alone exceeds 1KB), so this is harmless for real programs. But a pathological input that produces a tiny valid output would be silently replaced.

3. Filename/path quoting injection
The filename is embedded raw into the Python one-liner: print(gimple_codegen.compile_to_gimple(src, %d, '%s'), end=''). A filename containing a single quote ', backslash \, or newline breaks the shell command → Python raises SyntaxError → rc≠0 → silent stub. Same risk for MOJO_HOME in PYTHONPATH='...'.

4. PYTHONPATH='.' CWD default
When MOJO_HOME is unset, pythonpath defaults to "." (the process CWD). Running the compiled binary from a directory that doesn't contain gimple_codegen.py → import gimple_codegen fails → silent stub. The Makefile stage2/stage3 targets work around this with MOJO_HOME=.. PYTHONPATH=.., but any other invocation without the env var fails silently.

5. cmd[1024] truncation
The command buffer is 1024 bytes. A long PYTHONPATH or filename (deep directory nesting, macOS long names) gets truncated mid-string → broken Python code → rc≠0 → stub.

6. Static buffer reuse
result_buf is a process-lifetime static char *. A second call in one process clobbers the first caller's pointer. In current usage: each --dump invocation is a separate process, so this is latent. But any compiled program that calls compile_to_gimple twice (e.g. a multi-file build) would silently corrupt earlier results.

4.4 Why it masks reality

doc/IMPL.md:302-309 documents the consequence:

mojo --dump's main .ci generation routes through a subprocess that runs the real interpreted tokenizer/parser, so make bootstrap's verify step gave no signal at all about whether the self-hosted Parser/tokenizer actually worked when executed — only the .tok/.ast diagnostic dump code calls the compiled Parser/py_tokenize directly, in-process, which is exactly where this surfaced.

The compiled py_tokenize silently produced an empty token stream for every input (because re.Pattern.finditer() had no codegen lowering → loop body dropped). Only the .tok dump exposed it. The shim ensures .ci output always comes from real Python, hiding whether the compiled backend works.

5. Bootstrap machinery

Three stages

Stage 1:  Python mojo.py --dump-full mojo.py  →  stage1/mojo.ci  (transitive closure)
Stage 2:  gcc -fgimple stage1/mojo.ci         →  stage2/mojo     (compiled binary)
Stage 3:  stage2/mojo --dump mojo.py           →  stage2/mojo.ci  (+ .tok .ast .pyi)
Stage 4:  stage2/mojo --dump mojo.py           →  stage3/mojo.ci  (idempotency check)
Verify:   stage1 == stage2 == stage3            for all artifacts

The Makefile drives this: make stage1, make stage2/mojo, make stage2, make stage3, make verify. Each stage target collects dump failures and reports at the end.

Key targets

TargetWhat it does
check-selfhostCompile + link guard only (does NOT execute — runtime still SIGSEGVs). Compiles mojo.py → binary via test_selfhost.py.
check-gimpleGIMPLE codegen unit suite (test_gimple.py).
check-runnerExecution tests via the interpreter (test_runner.py).
check-modcacheModule cache end-to-end stages (test_module_cache.py).
mojocOne-step build: python3 mojo.py build mojo.py -o mojoc.
bootstrapFull end-to-end: stage1→2→3 + verify + validate-all.

6. Roadmap to remove the shim

What's already working

  • Compiled py_tokenize + Parser — once the regex engine (regex_compile.py + mojo_regex_search) enabled the compiled tokenizer's .finditer() loop, a cascade of self-host bugs was exposed and fixed (NULL deref, short-circuit semantics, varargs sentinel overwrites). The compiled tokenizer now produces correct token streams.
  • .tok / .ast dumps — these call compiled Parser/py_tokenize directly, confirming the compiled parser works for the project's own source.
  • Stage 2/3 bootstrap — make verify confirms byte-identical .ci outputs across stages (though .ci still comes from the shim).

The remaining frontier

Disable the interception at gimple_codegen.py:9175-9218 so the compiled binary calls its own compiled compile_to_gimple / gen_module natively. The compiled gen_module is the largest single function in the closure (~10k lines of compiled Python AST-walking and C-generation). It has never run natively.

Steps

  1. Temporarily remove the interception (comment out lines 9175-9218, or add a runtime flag) so the compiled compile_to_gimple is called as an ordinary module function.
  2. Rebuild mojoc / build/mojo from the modified source.
  3. Run --dump on a small file (e.g. test_simple.mojo or a minimal def main(): print(42)).
  4. Observe the first bugs — likely in compiled gen_module, GimpleGen internals, or the compiled py_tokenize / Parser pipeline when invoked from inside the codegen (vs. the .tok path).
  5. Fix bugs iteratively, rebuild, re-test.
  6. When byte-identical with Python's output for the test corpus, delete the shim: remove the interception (gimple_codegen.py:9175-9218), the C shim (runtime/mojo_runtime.c:2296-2377), the forward declaration (gimple_codegen.py:25371), the extern registration (gimple_codegen.py:16935), and the int_parse_module stub (runtime/mojo_runtime.c:2405).
  7. Verify: make check + make bootstrap + stdlib dylib rebuild (skip count unchanged).

Quality gates

Any change to gimple_codegen.py / module_loader.py / mojo_runtime.c (the compiled path) must pass:

  1. make check-selfhost — compile + link guard.
  2. From-scratch stdlib dylib build — rm -f build/libmojostdlib.dylib then python3 -c "import build_stdlib_dylib as bsd; bsd.build_stdlib(jobs=8)". Compare the skip <module>: count before/after; it must not increase.

A change passing test_gimple.py/test_module_cache.py/make check-selfhost alone is NOT sufficient evidence the compiled path is unaffected — only the stdlib build exercises the breadth of real Mojo source the compiler needs to keep working.
