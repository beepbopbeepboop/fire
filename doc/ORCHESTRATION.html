Orchestration guide

How the mojo-reference fleet is run: workers, mergers, claims, the gate, and the monitoring loop. Written 2026-10-17 and revised in full on 2026-11-12 to match the code (tools/swarm.py, tools/integrate.py, tools/control.py, tools/pool.json, tools/gates.json); so that any capable agent (including an opencode model, with no Claude subagents available) can read it, understand the system, and run it. Everything here was learned by running it; the incident list in §13 is the reason for most of the rules. When this file and the code disagree, the code (tools/control.py, tools/suite.py) wins: read it, then fix this file.

The design in one line: workers only commit to their own branch; one integrator lands branches on master, serialized, and finishes the job itself (the landed task's worktree, branch and registry entry go with the landing, §4); control.py cleanup is only a safety net for what the normal path cannot handle (a reboot, a killed worker, a bug). A growing pile of branches or worktrees is a bug in the flow, never a chore for cleanup.
If you are the agent reading this cold: do §1, then §12 (your first twenty minutes). Do not start workers, merge, or run a gate before you have done §12 steps 1-6. The owner (the user) gives standing instructions in chat; §14 lists the ones in force today.

2. Environment, paths, python, models

Python

Interpreter. Use /opt/local/bin/python3 (3.14.8) or the homebrew 3.15 (/opt/homebrew/bin/python3, 3.15.0 since 2026-10-18). 3.15 is fine for the fleet. The project moves everything to it later, not yet. /usr/bin/python3 is 3.9 and is not usable.

Known difference, measured on master at 15a260a3: test_formal_run.py reports FAIL=18 under 3.14 and FAIL=32 under 3.15 on the same commit, because CPython 3.15 reworded the % TypeError that tests assert on. Those fourteen extra failures come from the interpreter, not the code. Keep this in mind when a formal test goes red after a python change. tools/suite.py resolves its jobs with PY = sys.executable, so the whole check inherits whichever interpreter launched it.

Check with python3 --version before believing ANY formal-test failure, and after any brew upgrade.

Classes. A doc's class is the directory it sits in: easy = bugs/*.md, mid = bugs/mid/, hard = bugs/hard/. Every doc starts easy; a doc that gets escalate_after (2) no-commit attempts moves up one class (the move is a file move, committed to master by the swarm once nothing unlanded touches the doc). A class with no slot and unserved_policy replan (today: hard) is not left to rot: its docs are decomposed into parts at servable classes (§5). A class decides which slots may run a doc (a slot's class, plus its also list); it does not limit how many docs are queued. The feeder fills free slots, not classes: a doc is queued whenever some slot that accepts its class has room.

Limits. A usage limit bans that model for its slot's recover_hours (ledger: .git/control/dead_models.json). A second limit within a day uses long_recover_days where the slot has one. Banned daily free tiers are asked one word at most every 12 h (control.py probe-free, which the swarm runs each pass). A task prefers the slot it was queued for and takes the first free, unbanned slot of its class otherwise.

To pick a model for one restarted worker: restart NAME --model M. A bare model outside the pool, for hand-run experiments only: spawn --model M.

Other tools in use

lean only via formal/lean.py::run_lean (bounded wall/CPU time). Local compiler binaries ./mojoc. gcc with -fgimple. Rosetta 2 is installed, so x86-64 test binaries run (arch -x86_64 /usr/bin/true to verify); x86 rows that were once red for "Bad CPU type" are now real signal.

The worker prompt template is tools/control_prompt.md (its rules: stay in its worktree, scratch in .tmp/, no gate, read CLAUDE.md, commit small, check claims, file bugs it cannot fix as bugs/<AREA>_slug.md, add tests with the change, no shortcuts).

4. Claims: how duplicate work is prevented (and how it failed)

A claim is a string such as bug:FORMAL_some_doc, module:os or a repo path. Two claims conflict when equal or one is a path-prefix of the other. spawn/refill refuse a task whose claims conflict with a task that holds them. A task holds its claims while it is running, or while it is not terminal and its branch has commits master lacks (holds_claims). A terminal task (integrated, abandoned, superseded) holds nothing, and neither does a dead worker that committed nothing, so a retry is never refused by a ghost. control.py claims prints exactly the holders.

The duplicate-work failure (found 2026-10-16): tools/formal_feed.py used to mark a task integrated (releasing its claims) the moment the worker exited, not when its branch had landed on master. Branches then sat unmerged for days, the bug docs looked free, and new workers re-fixed the same bugs. Measured over the registry: 750 distinct bug docs dispatched across 758 dispatches; 522 fixed, of which 341 in one dispatch and 181 needed two or more; 1,214 dispatches spent on 522 fixed docs. The merge logs show "master-side parallel form" and "fifth parallel set-algebra implementation". Fix (commit d20d1466): formal_feed.release_finished now keeps the claims of an exited task whose branch still has commits master lacks (git rev-list --count master..BRANCH > 0).

State transitions. A task moves through these states; only the transitions listed are valid. DONE to DONE is NOT a valid transition: once a task reports DONE (and its branch is landed or its doc is deleted), it cannot be re-dispatched as DONE again. The DONE ratchet enforces this by skipping any doc already deleted on any branch.

A task's end cleans up after itself (2026-11-12). The normal path leaves nothing for a later pass: every terminal transition runs control.retire_task (landing runs retire_landed from integrate.mark_landed; control.py mark <terminal> and gate_doc run it too). The last column says what that removes. A tree is removed only when its only differences are the controller's own files (TASK.md, work.log, exitcode, .tmp/); a tree holding anything of the worker's is kept and reported, never forced.

control.py cleanup is the safety net, not part of the flow: it handles what the normal path cannot (a machine reboot, a killed worker, a registry entry from before these rules, a bug in the algorithm). It also retires branches nothing will land: a branch whose tip another branch already contains is deleted (lossless), and a terminal+held or registry-less one is archived under refs/archive/ first (git branch <name> refs/archive/<name> restores it).

Never. A task that wrote an exitcode file has finished: state_of already reports exited-ok/exited-err for it, so restarting it supersedes finished work (2026-11-10: r329 said DONE, exited 0, and sync --restart-dead restarted it anyway, superseding a finished task). A dead worker is never restarted into a slot that is disabled (count 0) or already at its count, or into a banned model — those can only fail again, which is what pinned one doc to an expired haiku OAuth session for 335 rounds. And a chain is never restarted past MAX_RESTARTS (10): over budget the task is abandoned, its claim is released, and the doc is re-fed (a fresh worker, possibly a different model). An authentication failure is a model failure, not a worker failure: it bans the model instead of restarting the worker.

A task in integrated or superseded or abandoned never transitions back to running or exited-ok. Re-dispatching the same bug doc creates a new task with a new name, and only if the doc still exists and is not ratcheted.

DONE ratchet (2026-11-09): a doc that any branch has already deleted is treated as resolved and is never re-dispatched, even while master still lists it and even if its claim was released. It is enforced in three places: the swarm's feed (tools/swarm.py), the formal feeder (tools/formal_feed.py), and control.py sync --restart-dead (which supersedes a dead task whose docs are all gone instead of restarting it). This is what stops the loop where a fixed bug is re-fixed forever.
The ratchet's premise must hold (2026-11-10): "deleted on a branch" only means fixed if that branch reaches master. A DONE task with commits is now landable in superseded/abandoned state too (it is finished work; a restart does not unsolve the bug), so the branch the ratchet relies on actually lands. Before this, 1030 fixed branches were stranded — the doc stayed on master, the ratchet skipped it, and no worker ever touched it. land() has no batch cap: the landing gate is cheap (stdlib compile), conflicts go to merge fixers inside the round and a red is bisected to its culprit, so everything finished lands in one pass. (The old cap of 8 let 14+ finished branches queue per pass and, with the crash below, a 24-branch backlog never drained.)
The cure is to land the finished branches (§7), not to release claims by hand. Hand-marking integrated is only right after you have verified the branch is on master (or truly worthless).

Before dispatching new work on a topic, also search for overlap the claim system cannot see (different docs, same subject): git branch --no-merged master | grep work/, git log master --oneline -S<identifier>, git cherry master BRANCH.

5. The swarm (feeder and landing loop)

tools/swarm.py is the one long-lived loop. It replaced the old keep-full script (keepfull.sh, retired). Start it from the main checkout, detached, with the right interpreter:

cd /Users/mrs/net/chatgpt/claude/mojo-reference
nohup /opt/homebrew/bin/python3 tools/swarm.py &
python3 tools/swarm.py --who        # who holds it (proved by the flock, not by a name match)
python3 tools/swarm.py --feed       # every doc the feed considers, grouped by why it waits (-v lists them)
python3 tools/swarm.py --why DOC    # why one doc is not being fed (what holds it)
kill -TERM <pid>                    # stop it: only the pid --who prints, after --who verified the command line
# state: .git/control/swarm.json   log: .git/control/swarm.out   lock and pid record: .git/control/swarm.pid
# --interval 120, --target (the pool total) and --log-file (.git/control/swarm.out) are the defaults

One pass, every --interval seconds, in this order. A pass that raises is logged as pass failed: ... and the loop survives; read that line, it is a bug.

  1. Reload and guard. A landed tools/*.py change re-execs the swarm so a fix reaches it. live_guard lists the opencode sessions: a tree a live session drives is busy, and no doc it holds is fed, continued, retired or landed. If the listing cannot be read, the pass feeds and lands nothing (fail closed).
  2. Class moves, reap, sync, cleanup. A doc due a class move moves once nothing unlanded touches it. reap stops the recorded process groups of finished workers. sync --restart-dead reconciles the registry (§3). cleanup runs as the safety net (§3).
  3. Replan, feed, continue, retire. Docs at a class with no slot (hard today) are decomposed by an easy-class replan task into parts (SPLIT: line in the original). Feed: enqueue docs until every free slot has work, drawn from the pool's feed globs, minus the skip list (OPEN_WORK, README), minus any doc a live task, queued task or external claim holds, minus any doc with a STOP: <reason> line, minus any doc a branch already deleted (the DONE ratchet, §4), minus a SPLIT doc whose parts exist. Continue: a worker that exited without DONE but with commits is continued by a new worker from its branch; a round with no new commits counts as no progress and moves the doc up a class. Retire: a dead-on-arrival attempt (no commits) is abandoned and its tree and branch go.
  4. Refill. control.py refill --target N --prefix bug-,fix- starts queued tasks into free slots (claims, bans and the circuit breaker permitting); a finished worker frees its slot at once. probe-free and cpu_cap ratchet run here.
  5. Land (§7). Every finished bug-*/fix-* branch lands in one round: no batch cap. Tasks with other names (hand-spawned, experiments) are never landed by the swarm; land them with integrate.py --only. After a landing the swarm starts tools/verify_landed.py in the background (the full gate, at most once per full_every_minutes, under the integrator lock; each red job becomes bugs/gate-<job>.md and a fix-gate-<job> task) and runs cleanup again.

Lines worth reading in swarm.out: GREEN: master fast-forwarded (a landing), conflict X: handing it to a merge fixer, red: X breaks the gate (held, a gate doc is the work), master moved under the round (see §7), no progress on DOC, reclass, pass failed. Repeats are suppressed for a few minutes, so a quiet log means an unchanged state.

Two other feeders exist and are separate: tools/formal_feed.py owns the FORMAL_ docs (the swarm never starts them), and tools/autointegrate.py is a separate integrator for that lane. Claims (§4) are what keeps them from colliding, so spawn and enqueue work through control.py, never by editing tasks.json by hand.

6. Writing a task (templates)

A task file is plain text given to spawn --task-file. A good one: states the goal and the docs, names the exact narrow commands, states what must not be touched, and tells the worker to check master. Common closing rules for every worker task:

Rules: you are a LIGHT worker. No gate, no `make check`/`make gate`, no bootstrap, no whole-closure compile; run only narrow tests via
`python3 tools/memslot.py --gb 8 --label t -- python3 ` (export PATH=/opt/homebrew/bin:$PATH). Lean only via formal/lean.py (time-bounded:
a valid proof is fast; one that is slow is wrong or needs a different formulation). Nothing of ours over 3-4 GB. Read CLAUDE.md first. Commit
often; delete a bug doc you fully fix and run `python3 tools/dangling_doc_refs.py --ratchet`. Finish with a clean tree, a short report, and
CONTROL-STATUS: DONE (or PARTIAL).

Bug-doc worker

Work through these bug docs, in order; each is yours alone:
  - bugs/FOO_a.md
  - bugs/FOO_b.md
Fix each for real (no time-boxing; no "re-verified, unchanged" outcomes; partial progress is committed and the doc's Status updated; a doc stale because the bug is fixed is `git rm`'d).
CHECK MASTER at the start and again before finishing: `git log --oneline master -20`; `git merge master` into your branch before you finish and reconcile.
+ the closing rules

Merger (the hard job; give it to the strongest model)

7. Integration: landing branches on master

Normally you do nothing here: the swarm lands. A round (tools/integrate.py --stdlib), under one exclusive lock:

  1. Pick finished work: tasks whose worker exited with a DONE verdict, commits master lacks, a clean tree, not held, not owned by a fixer, not merge_capped. superseded and abandoned DONE tasks count: finished work is still finished after a restart. A branch that deletes a bug doc without changing a test file is not picked (a person lands it).
  2. Merge each into integ in ../work-integ (--no-ff). A branch that conflicts is left out and handed to a merge fixer (fix-merge-*; chains deeper than 3, or with no doc for a fixer to serve, are abandoned and merge_capped).
  3. Gate the result with the landing gate only (§8). Red: find_culprit bisects the batch, the culprit is held first, filed as bugs/gate-<job>.md (job names only; failing files go in the body) and archived under refs/archive/; the rest of the batch is probed again and lands. A red that does not reproduce when re-run alone is treated as load and goes green.
  4. Move master once by git merge --ff-only integ in the main checkout, through stash_ff (your uncommitted edits are carried across; only a real textual conflict with them makes the landing wait, with your files untouched). If master moved while the round gated (other lanes land here too): a move in no file or only controller files is merged over; a move in real files is merged into the round, the landing gate re-runs on that result, and the fast-forward is retried (3 tries). A conflict or a red re-gate stops with master untouched. Redoing the whole round instead never converges on a busy machine.
  5. Finish the job. mark_landed sets integrated (refusing if any commit is not on master), then retire_landed removes the task's worktree, deletes its branch and drops its registry entry (§4). Nothing waits for a later cleanup pass.

Serialization: integrator.lock (an flock, released by the kernel if the process dies) admits one integrator at a time; the swarm's probes, its landing and verify_landed.py all take it, so “integrator busy” just means “next pass”. A round moves master once, however many branches it holds.

By hand (the swarm stopped, or a task with another name): python3 tools/integrate.py --stdlib --only NAME... does the same round for exactly those tasks (the order given is the merge order). --probe merges and gates changing no state; --dry-run only merges.

A bulk merge by an operator (many large branches at once, resolved by hand) is a different job and keeps its older rules:

  1. Try the plain merge first in a clean tree: git merge --no-edit work/NAME; on conflict git merge --abort and give it to a merge fixer. Conflicts in generated files (tools/dangling_refs_baseline.py, doc indexes): keep the union, regenerate with the tool.
  2. After any merge: python3 tools/dangling_doc_refs.py --ratchet (must not gain a citation) and a compile() sweep of every tracked .py (ast.parse misses duplicate arguments).
  3. Verify large merges with suite.py check in gate-wt before trusting them (the two bulk merges of 374 and 444 commits each left 6 red jobs). Fix forward on master.
  4. Delete fixed bug docs in the same commit as the fix.
Why "resolve to master's side" is dangerous: bulk merges that resolved every conflict to master's side silently dropped the branch's half of shared signatures, import blocks and definitions while keeping the branch's bodies: NameErrors, TypeError: unexpected keyword argument, duplicate definitions, half-applied fixes (a fix landed, a later merge took one side and reverted its test half). Rule: keep both halves; verify with compile(), an undefined-name check, and the narrow tests.

9. The monitoring loop (every 50 minutes)

The owner asked for a check every 50 minutes (keeps the model prompt cache warm). The swarm does the work; the operator checks that it is flowing. Each tick, in this order (a few commands; do not narrate unchanged state):

  1. Swarm alive: python3 tools/swarm.py --who and tail -5 .git/control/swarm.out. A traceback, a pass failed line or a silent log is a bug: read it, fix it, restart (§5).
  2. Flow, not pile-up: git for-each-ref --no-merged master 'refs/heads/work/*' | wc -l should be about the live work (running plus a few waiting to land), and git worktree list | wc -l similar.   3. Stuck work: python3 tools/control.py claims (should be running tasks plus finished-but-unlanded ones, and the latter should land within a pass or two); python3 tools/swarm.py --feed (what waits and why; a large “held” group means landing is stalled).

  5. Hard-problem agents: their worktree (.claude/worktrees/agent-*): commits ahead, dirty, behind master. If they stopped on a session limit, try resuming once the stated reset time has passed.
  6. Verification: .git/control/verify.json and any bugs/gate-*.md (red jobs and their work).
  7. Resources: df -h /, load average.
  8. Report to the owner in plain text: what changed, what landed, what is red and why. Never assert a cause without the log line that shows it.

11. Memory, disk, processes

Kill rules (2026-11-02, after the process losses).
  1. The fleet signals only processes it spawned and recorded. Every spawn is written to .git/control/spawned.jsonl with its pid, process group and start time (tools/fleet_ledger.py). Nothing else is ever signalled.
  2. Nothing is matched by working directory, command name or port. A process in a worktree is not ours unless it is in a recorded group.
  3. A user's own opencode session, and anything an outside session has claimed (control.py claim, including a claimed workdir), is never signalled and never removed. cleanup skips such trees.
  4. To stop a recorded worker, the fleet sends SIGTERM to its process group and waits 20 s so the workload can save. SIGKILL is sent only if the group is still alive after that wait. A recorded group whose leader has exited is not signalled; its members are logged and left alone.
  5. A recorded group is stopped only when its leader still has the start time recorded at spawn. A recycled pid is refused.
  6. Every spawn, signal, refusal and skip is appended to .git/control/kills.log. Read it before you decide anything about a process.
  7. Do not signal a process or session by hand. Do not interrupt or delete an opencode session the fleet did not start. If something must stop, ask the owner first.
Workers started before this rule have no record, so the fleet never signals them.
  • The machine has a 96 GB memory budget shared by everything, enforced by tools/memslot.py (strict FIFO reservations). Anything heavy goes through the suite runner or python3 tools/memslot.py --gb N --label X -- CMD; the current holds: python3 tools/memslot.py status. Classes: tiny 4, small 8, module 24, program 55, stage 96 GB; each class comes from a measured peak (MEASURED_PEAK_GB in suite.py). Anything of ours over 3-4 GB is itself a bug (doc/POLICY_memory_over_4gb.md).
  • Every worker runs under a CPU-time cap (tools/cpu_cap.py, RLIMIT_CPU: SIGXCPU, then SIGKILL a minute later), which ratchets down from measured runs, so a stuck loop stops itself. The worker's last log line says how much it used (e.g. used 485 s of a 600 s cap).
  • Workers must not run the gate or whole-closure compiles; hard-problem agents may run one bootstrap at a time (~30 min) through the runner.
  • Disk: df -h /; control.py cleanup above ~85%. Never clear ~/.gmojo/cas (content-addressed, self-invalidating; clearing only forces cold rebuilds). tools/clean-gmojo.py prunes old entries by age.
  • Never kill the owner's own opencode sessions (ps shows them as "belong to someone else"), any session with an outside claim, or the omlx server. The fleet signals only process groups it recorded at spawn (§11 kill rules): SIGTERM first, SIGKILL only after the grace period, and never a process the fleet did not start.
  • Lean must be bounded: a proof check that runs long is a bug. Ten Lean processes once ran for hundreds of CPU-hours; formal/lean.py::run_lean bounds wall/CPU time itself. guard does not check Lean time.
