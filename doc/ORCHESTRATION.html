Written 2026-10-17 so that any capable agent (including an opencode model, with no Claude subagents available) can read it, understand the system, and run it. Everything here was learned by running it; the incident list in §13 is the reason for most of the rules. When this file and the code disagree, the code (tools/control.py, tools/suite.py) wins: read it, then fix this file.

If you are the agent reading this cold: do §1, then §12 (your first twenty minutes). Do not start workers, merge, or run a gate before you have done §12 steps 1-6. The owner (the user) gives standing instructions in chat; §14 lists the ones in force today.

1. Roles and the shape of the system

The repo is /Users/mrs/net/chatgpt/claude/mojo-reference (the main checkout, branch master). It is a Mojo compiler/interpreter (Python) with several backends and a formal-verification backend (arm64 + x86-64 Mach-O, Lean proofs). The work is a very large backlog of bug docs in bugs/ (the queue) worked by many parallel AI workers.

3. control.py: the controller

All commands are python3 /Users/mrs/net/chatgpt/claude/mojo-reference/tools/control.py <cmd>. Use that absolute path (your cwd may be a worktree; control.py derives its main-checkout paths from its own location, so always run the main checkout's copy).

CommandPurpose / gotchas
psLive workers. Names show as ? for workers launched with the v2 command (known cosmetic bug; match by pid/worktree via ps -axww -o pid,etime,args and the --title NAME in the args). Also reports "N other opencode processes belong to someone else" (the owner's own sessions: never touch them).
statusOne line per task: name, work-N, state (running, exited-ok, exited-err, integrated, superseded, abandoned), CONTROL-STATUS, commits ahead, dirty files. State integrated does NOT mean the branch is on master — see §4.
spawn NAME --claim K [--claim K...] (--task TEXT | --task-file F) [--model M] [--base BRANCH]Creates the worktree and starts a worker now. Refuses if a claim conflicts. A name that already exists is refused ("task NAME already exists"): pick a new one.
enqueue NAME ... / queue / refill --target NQueue a task; refill starts queued tasks oldest-first while fewer than N workers run and claims are free. Queue order is FIFO; priority is only for integration order, not start order.
restart NAME [--model M] [--why TEXT]Snapshots the worker's uncommitted work with git add -A && git commit, stops it, continues it as NAME-r2 from its branch with a fresh session. Never restart a worker that is mid-merge with unresolved conflicts: the snapshot commits literal conflict markers (it happened; the new worker must be told to run git grep -n -E '^(<<<<<<<|=======|>>>>>>>)' first, which works but is ugly). Restarting is right for a stalled or early-stopped worker.
unstickRestarts workers whose log is idle AND whose tree uses no CPU.
claimsAll live claims.

guard [--once]Watchdog: kills process trees of ours over 55 GB each / 90 GB total, Lean past 45 min wall / 90 min CPU, and runaway fire.py build/test_*.py/probes past 120 min. Does not cover native test binaries or CPU-burning opencode processes. The keep-full loop runs it with --once every pass.
reap, cleanup [--dry-run]reap kills leftover lean/gcc in finished workers' trees; cleanup removes worktrees whose HEAD is an ancestor of master, are clean and not running (keeps branches). Run it when disk is above ~85%.

Workers finish by printing exactly one of CONTROL-STATUS: DONE | PARTIAL | NEEDS-INFO | BLOCKED. The worker prompt template is tools/control_prompt.md (its rules: stay in its worktree, scratch in .tmp/, no gate, read CLAUDE.md, commit small, check claims, file bugs it cannot fix as bugs/<AREA>_slug.md, add tests with the change, no shortcuts).

4. Claims: how duplicate work is prevented (and how it failed)

A claim is a string such as bug:FORMAL_some_doc, module:os or a repo path. Two claims conflict when equal or one is a path-prefix of the other. spawn/refill refuse a task whose claims conflict with any task not in a terminal state. A claim is held until the task is marked integrated/abandoned/superseded.

The duplicate-work failure (found 2026-10-16): tools/formal_feed.py used to mark a task integrated (releasing its claims) the moment the worker exited, not when its branch had landed on master. Branches then sat unmerged for days, the bug docs looked free, and new workers re-fixed the same bugs. Measured over the registry: 750 distinct bug docs dispatched across 758 dispatches; 522 fixed, of which 341 in one dispatch and 181 needed two or more; 1,214 dispatches spent on 522 fixed docs. The merge logs show "master-side parallel form" and "fifth parallel set-algebra implementation". Fix (commit d20d1466): formal_feed.release_finished now keeps the claims of an exited task whose branch still has commits master lacks (git rev-list --count master..BRANCH > 0).

Consequence you must manage: when many finished branches are unmerged, queued tasks that name the same docs are skipped ("claim ... conflicts with ... held by task X") and the fleet starves. The cure is to land the finished branches (§7), not to release claims by hand. Hand-marking integrated is only right after you have verified the branch is on master (or truly worthless).

Before dispatching new work on a topic, also search for overlap the claim system cannot see (different docs, same subject): git branch --no-merged master | grep work/, git log master --oneline -S<identifier>, git cherry master BRANCH.

5. The keep-full loop

/Users/mrs/net/chatgpt/claude/keepfull.sh (run detached: nohup ./keepfull.sh > keepfull.log 2>&1 &, kill with pkill -f keepfull.sh):

#!/bin/bash
export PATH=/opt/homebrew/bin:$PATH
export CONTROL_MODEL=opencode-go/deepseek-v4.1-flash
cd /Users/mrs/net/chatgpt/claude/mojo-reference
while true; do
  python3 tools/formal_feed.py --min-ready 12      # release landed tasks' claims, enqueue more FORMAL docs / projects
  total=$(python3 tools/control.py ps | tail -1 | awk '{print $1}')
  ds=$(ps -axww -o args= | awk '$1 ~ /opencode$/ && $2=="run" && /opencode-go\/deepseek/' | wc -l)
  python3 tools/control.py refill --target $(( total - ds + 1 ))   # exactly ONE DeepSeek worker; others (bunny, Qwen, mergers) don't count
  python3 tools/control.py guard --once 2>/dev/null
  sleep 300
done

It keeps the queue stocked from FORMAL docs nobody holds and from tools/formal_projects.json (each key enqueued once ever; used keys in control/feed.json; that backlog is exhausted), and starts workers only while claims are free. If it prints a Python error such as "No such file or directory", restart it (it caches command paths). Change the DeepSeek count by editing + 1.

refill with a large --target is also how you start a specific queued task out of order for a moment (e.g. a merger stuck behind formal tasks).

6. Writing a task (templates)

A task file is plain text given to spawn --task-file. A good one: states the goal and the docs, names the exact narrow commands, states what must not be touched, and tells the worker to check master. Common closing rules for every worker task:

Rules: you are a LIGHT worker. No gate, no `make check`/`make gate`, no bootstrap, no whole-closure compile; run only narrow tests via
`python3 tools/memslot.py --gb 8 --label t -- python3 ` (export PATH=/opt/homebrew/bin:$PATH). Lean only via formal/lean.py (time-bounded:
a valid proof is fast; one that is slow is wrong or needs a different formulation). Nothing of ours over 3-4 GB. Read CLAUDE.md first. Commit
often; delete a bug doc you fully fix and run `python3 tools/dangling_doc_refs.py --ratchet`. Finish with a clean tree, a short report, and
CONTROL-STATUS: DONE (or PARTIAL).

Bug-doc worker

Work through these bug docs, in order; each is yours alone:
  - bugs/FOO_a.md
  - bugs/FOO_b.md
Fix each for real (no time-boxing; no "re-verified, unchanged" outcomes; partial progress is committed and the doc's Status updated; a doc stale because the bug is fixed is `git rm`'d).
CHECK MASTER at the start and again before finishing: `git log --oneline master -20`; `git merge master` into your branch before you finish and reconcile.
+ the closing rules

Merger (the hard job; give it to the strongest model)

You are a MERGER. Your branch starts at master. Merge these finished branches into it, oldest first, one at a time, committing each:
  work/a  work/b ...
(For each: `git cherry master ` — only '-' lines means already landed: skip.) Resolve conflicts keeping BOTH sides' intent.
NEVER resolve by taking one whole side when both sides changed a shared signature, import block or definition: keep the branch's half of those.
After EACH merge: `compile()` (not ast.parse) over every `git ls-files '*.py'`, an undefined-name check on the files touched, and the narrow
test_formal_*.py for them. Two competing mechanisms for one construct: satisfy the UNION of both sides' tests and say why in the commit message.
Run `python3 tools/dangling_doc_refs.py --ratchet`. No gate, no bootstrap/mojo/ work. `git merge master` before finishing. CONTROL-STATUS: DONE.

Hard-bug agent

Same as a bug-doc worker, plus: state how correctness is proved (e.g. "byte-identical generated C before and after, cmp the artifacts, plus test_selfhost.py"), say the gate is the controller's, and name which areas belong to another agent.

7. Integration: landing branches on master

  1. Find finished work. status | grep -E 'DONE|PARTIAL' and, authoritative, git for-each-ref --no-merged master --format='%(refname:short)' 'refs/heads/work/*'. Skip branches of workers still running.
  2. Try the plain merge first (in the main checkout, clean tree): git merge --no-edit work/NAME. If it conflicts: git merge --abort and give the branch to a merger. Small conflicts in generated/baseline files (tools/dangling_refs_baseline.py, doc indexes) you can resolve yourself: keep the union, then regenerate with the tool.
  3. After any merge: python3 tools/dangling_doc_refs.py --ratchet (must not gain a citation) and a compile() sweep of every tracked .py (ast.parse misses duplicate arguments).
  4. Verify bulk merges before trusting them: run python3 tools/suite.py check (about 10 minutes) in gate-wt on the branch tip before merging it to master when it is large (the two bulk merges of 374 and 444 commits each left 6 red jobs). Fix forward on master.
  5. Mark landed tasks integrated only after the merge (the feed does this automatically once git rev-list --count master..BRANCH is 0).
  6. Formal-only changes need no gate (owner's rule). Anything touching fire_compiler.py, gimple_codegen.py, mojo/**, runtime/**, module_loader.py, myinterpreter.py owes a full gate (§8) once, after the batch.
  7. Delete fixed bug docs in the same commit as the fix (a doc is a queue entry; a fixed bug listed is indistinguishable from an open one).
Why "resolve to master's side" is dangerous: bulk merges that resolved every conflict to master's side silently dropped the branch's half of shared signatures, import blocks and definitions while keeping the branch's bodies: NameErrors, TypeError: unexpected keyword argument, duplicate definitions, half-applied fixes (a fix landed, a later merge took one side and reverted its test half). Rule: keep both halves; verify with compile(), an undefined-name check, and the narrow tests. See bugs/MERGE_bulk_resolved_to_master_dropped_branch_definitions.md for the open follow-up queue.

8. The gate and check

tools/suite.py is the only definition of what is tested. python3 tools/suite.py check is the everyday subset (about 53 jobs, ~9-10 min); gate = check + coro + stdlib + native + bootstrap (~35 min, tens of GB). Never restate bucket membership: python3 tools/suite.py --list is the truth. Read CLAUDE.md's "Running the checks", "quality gate" and "Known failures" sections: the markers and rules there are binding.

How to run one

cd /Users/mrs/net/chatgpt/claude/gate-wt && export PATH=/opt/homebrew/bin:$PATH
git checkout -q --detach master            # or the branch tip you want to verify
nohup python3 tools/suite.py check > ../check-X.log 2>&1 &      # or `gate`
# result: last line of ../check-X.log "suite: N passed, M failed ..."; details: gate-wt/build/suite.log
tr -d '\033' < ../check-X.log | awk '/^FAILED/{f=1} f&&/^(EXPECTED|DISABLED|SKIPPED|suite:)/{f=0} f'     # the failing jobs
awk '/--- output: last 40 lines of JOBNAME ---/{f=1} f' build/suite.log | head -40          # one job's output

One gate at a time per machine (memory). Do not touch gate-wt while a run is using it; give hard-problem agents their own worktrees.

Reading it

  • expect='why' = known cheap failure (an expect-marked test that PASSES is reported as a FAILURE: drop the marker). disabled='bugs/DOC.md' = known expensive failure, not run; the doc is the switch (deleting it re-enables the test).
  • Two gate verdicts need judgement beyond exit 0: stdlib-dylib (the count of skip <module>: must not rise) and stdlib-syntax (FAILED: N (E expected, U unexpected): U must not rise).
  • Fanout jobs (bootstrap-stage2-dumps) print many FAIL job:item lines that are absorbed by an expect= count; look at the FAILED section, not those lines.
  • After a gate: if the log prints PEAK DRIFT, run python3 tools/suite.py --apply-peaks build/suite.log [--dry-run] and re-class the jobs it names (only for jobs that PASSED and ran at least 2 s).
  • Flake seen once: x86-examples "toplevel_const: 'LIMIT' has no home" under parallel load; passes alone. Re-run before declaring a regression.
  • Jobs registered but not in check (formal-run, formal-value-model, formal-peephole, test_formal_call_proof_gen.py, ...) are not reported by check; run them narrowly when working in their area.

9. The monitoring loop (every 50 minutes)

The owner asked for a check every 50 minutes (keeps the model prompt cache warm). Each tick, in this order (keep it to a few commands; do not narrate unchanged state):

  1. Fleet: control.py ps; for each running worker compare work.log mtime to now and look at git -C ../work-N rev-list --count master..HEAD and status --short | wc -l. A log untouched for >30 min with ~0% CPU = stalled (§10).
  2. Finished: status | grep -E 'exited|DONE|PARTIAL' and the unmerged-branches list. Land what is finished (§7).
  3. Hard-problem agents: their worktree (.claude/worktrees/agent-*): commits ahead, dirty, behind master. If they stopped on a session limit, try resuming once the stated reset time has passed.
  4. Queue and keep-full: tail -3 keepfull.log. Starvation ("skip ... claim conflicts") means unmerged branches are holding claims: land them.
  5. Verification: any pending check/gate log? Read its FAILED section and act (§8).
  6. Resources: df -h / (cleanup above ~85%), load average.
  7. Report to the owner in plain text: what changed, what landed, what is red and why. Never assert a cause without the log line that shows it.

11. Memory, disk, processes

  • The machine has a 96 GB memory budget shared by everything, enforced by tools/memslot.py (strict FIFO reservations). Anything heavy goes through the suite runner or python3 tools/memslot.py --gb N --label X -- CMD; the current holds: python3 tools/memslot.py status. Classes: tiny 4, small 8, module 24, program 55, stage 96 GB; each class comes from a measured peak (MEASURED_PEAK_GB in suite.py). Anything of ours over 3-4 GB is itself a bug (bugs/PERF_memory_over_4gb_is_a_bug.md).
  • Workers must not run the gate or whole-closure compiles; hard-problem agents may run one bootstrap at a time (~30 min) through the runner.
  • Disk: df -h /; control.py cleanup above ~85%. Never clear ~/.gmojo/cas (content-addressed, self-invalidating; clearing only forces cold rebuilds). tools/clean-gmojo.py prunes old entries by age.
  • Never kill the owner's own opencode sessions (ps shows them as "belong to someone else"); never kill the omlx server. Kill only our worker trees, and prefer restart/guard over kill -9.
  • Lean must be bounded: a proof check that runs long is a bug. Ten Lean processes once ran for hundreds of CPU-hours; formal/lean.py::run_lean now bounds wall/CPU time and guard backs it up.

14. Standing instructions from the owner (in force as of 2026-10-17)

  • Never lose work. Never discard uncommitted work; no git checkout <path>/git restore <path>/git stash. Each bug is fixed once; check master and unmerged branches before dispatching.
  • Workers are light (no gate, no heavy builds). The controller runs the gate once per batch. Formal work needs no gate, not even the usual formal gate. Formal rows that take unbounded time are marked, not waited on.
  • No time-boxing of bug work. A fixed bug's doc is deleted in the same commit; run the citation ratchet.
  • Model policy: exactly one DeepSeek worker; space-bunny for hard problems and hard merges; Qwen local is slow; big-pickle shares DeepSeek's bucket; a bunny that stops without an error line is restarted, not "rate limited". Bootstrap belongs to one hard-problem agent (do not duplicate it).
  • Check workers every 50 minutes. Record the facts, not guesses. Do not claim a cause you have not seen in a log.
  • Prefer production-quality fixes over quick ones; consolidate duplicates; keep leftover processes and disk under control.
