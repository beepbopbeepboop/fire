Written 2026-10-17 and revised 2026-11-02 to match the code (tools/swarm.py, tools/pool.json, tools/control.py); so that any capable agent (including an opencode model, with no Claude subagents available) can read it, understand the system, and run it. 1. Roles and the shape of the system

The repo is /Users/mrs/net/chatgpt/claude/mojo-reference (the main checkout, branch master). It is a Mojo compiler/interpreter (Python) with several backends and a formal-verification backend (arm64 + x86-64 Mach-O, Lean proofs). The work is a very large backlog of bug docs in bugs/ (the queue) worked by many parallel AI workers.

2. Environment, paths, python, models

Python

Interpreter. Use /opt/local/bin/python3 (3.14.8) or the homebrew 3.15 (/opt/homebrew/bin/python3, 3.15.0 since 2026-10-18). 3.15 is fine for the fleet. The project moves everything to it later, not yet. /usr/bin/python3 is 3.9 and is not usable.

Known difference, measured on master at 15a260a3: test_formal_run.py reports FAIL=18 under 3.14 and FAIL=32 under 3.15 on the same commit, because CPython 3.15 reworded the % TypeError that tests assert on. Those fourteen extra failures come from the interpreter, not the code. Keep this in mind when a formal test goes red after a python change. tools/suite.py resolves its jobs with PY = sys.executable, so the whole check inherits whichever interpreter launched it.

Check with python3 --version before believing ANY formal-test failure, and after any brew upgrade.

opencode (v2.0.26 syntax: this changed and broke everything once)

# a worker is launched as (control.py does this for you; cwd = the worktree):
opencode run --model PROVIDER/MODEL --auto --title NAME "Your complete instructions are in /path/work-N/TASK.md. Read it now and follow it exactly."

The model ids differ, so limits, bans and the ledger (dead_models.json, keyed by model id) apply to each separately. Do not treat one as a fallback for the other.

Classes. A doc's class is the directory it sits in: easy = bugs/*.md, mid = bugs/mid/, hard = bugs/hard/. Every doc starts easy; a doc that gets escalate_after (2) no-commit attempts moves up one class. A class decides which slots may run a doc (a slot's class, plus its also list); it does not limit how many docs are queued. The feeder fills free slots, not classes: a doc is queued whenever some slot that accepts its class has room.

Limits. A usage limit bans that model for its slot's recover_hours (ledger: .git/control/dead_models.json). A second limit within a day uses long_recover_days where the slot has one. Banned daily free tiers are asked one word at most every 12 h (control.py probe-free, which the swarm runs each pass). A task prefers the slot it was queued for and takes the first free, unbanned slot of its class otherwise.

To pick a model for one restarted worker: restart NAME --model M. A bare model outside the pool, for hand-run experiments only: spawn --model M.

Other tools in use

lean only via formal/lean.py::run_lean (bounded wall/CPU time). Local compiler binaries ./mojoc. gcc with -fgimple. Rosetta 2 is installed, so x86-64 test binaries run (arch -x86_64 /usr/bin/true to verify); x86 rows that were once red for "Bad CPU type" are now real signal.

All commands are python3 /Users/mrs/net/chatgpt/claude/mojo-reference/tools/control.py <cmd>. Use that absolute path (your cwd may be a worktree; control.py derives its main-checkout paths from its own location, so always run the main checkout's copy).

The worker prompt template is tools/control_prompt.md (its rules: stay in its worktree, scratch in .tmp/, no gate, read CLAUDE.md, commit small, check claims, file bugs it cannot fix as bugs/<AREA>_slug.md, add tests with the change, no shortcuts).

4. Claims: how duplicate work is prevented (and how it failed)

A claim is a string such as bug:FORMAL_some_doc, module:os or a repo path. Two claims conflict when equal or one is a path-prefix of the other. spawn/refill refuse a task whose claims conflict with any task not in a terminal state. A claim is held until the task is marked integrated/abandoned/superseded.

The duplicate-work failure (found 2026-10-16): tools/formal_feed.py used to mark a task integrated (releasing its claims) the moment the worker exited, not when its branch had landed on master. Branches then sat unmerged for days, the bug docs looked free, and new workers re-fixed the same bugs. Measured over the registry: 750 distinct bug docs dispatched across 758 dispatches; 522 fixed, of which 341 in one dispatch and 181 needed two or more; 1,214 dispatches spent on 522 fixed docs. The merge logs show "master-side parallel form" and "fifth parallel set-algebra implementation". Fix (commit d20d1466): formal_feed.release_finished now keeps the claims of an exited task whose branch still has commits master lacks (git rev-list --count master..BRANCH > 0).

State transitions. A task moves through these states; only the transitions listed are valid. DONE to DONE is NOT a valid transition: once a task reports DONE (and its branch is landed or its doc is deleted), it cannot be re-dispatched as DONE again. The DONE ratchet enforces this by skipping any doc already deleted on any branch.

FromToTrigger
queuedrunningspawn / refill starts the worker
runningexited-okworker prints CONTROL-STATUS: DONE
runningexited-errworker prints PARTIAL / BLOCKED or exits nonzero
runningsupersededrestart (snapshot + continue as NAME-r2)
exited-okintegratedbranch lands on master (rev-list master..BRANCH == 0)
exited-okabandonedmanually declared worthless
exited-errsupersededrestart from the failed attempt
integrated(terminal)claims released; doc deleted; no re-dispatch
superseded(terminal for old task)new task holds the claims; old task is gone
abandoned(terminal)claims released

A task in integrated or superseded or abandoned never transitions back to running or exited-ok. Re-dispatching the same bug doc creates a new task with a new name, and only if the doc still exists and is not ratcheted.

DONE ratchet (2026-11-09): a doc that any branch has already deleted is treated as resolved and is never re-dispatched, even while master still lists it and even if its claim was released. It is enforced in three places: the swarm's feed (tools/swarm.py), the formal feeder (tools/formal_feed.py), and control.py sync --restart-dead (which supersedes a dead task whose docs are all gone instead of restarting it). This is what stops the loop where a fixed bug is re-fixed forever.
The cure is to land the finished branches (§7), not to release claims by hand. Hand-marking integrated is only right after you have verified the branch is on master (or truly worthless).

Before dispatching new work on a topic, also search for overlap the claim system cannot see (different docs, same subject): git branch --no-merged master | grep work/, git log master --oneline -S<identifier>, git cherry master BRANCH.

5. The swarm (feeder and landing loop)

tools/swarm.py is the one long-lived loop. It replaced the old keep-full script (keepfull.sh, which is no longer started: its last log line is 2026-11-02 12:07 and it still names one model). Start it from the main checkout, detached, with the right interpreter:

cd /Users/mrs/net/chatgpt/claude/mojo-reference
nohup /opt/local/bin/python3 tools/swarm.py &
# who holds it (proved by the flock, not by a name match):  python3 tools/swarm.py --who
# stop the pid --who prints (it verifies the command line first):  kill -TERM 
# state: .git/control/swarm.json   pid record and lock: .git/control/swarm.pid
# --interval 120, --target (pool total) and --log-file (.git/control/swarm.out) are the defaults

One pass, every --interval seconds:

  1. Class moves and reap. A doc due a class move moves once nothing unlanded touches it and no live opencode session is working on it. control.py reap stops the recorded process groups of finished workers, and nothing else.
  2. Feed. Enqueue queued tasks until every free slot has work (one per free slot, plus one buffer), drawn from the pool's feed globs in pool order, minus the pool's skip prefixes (FORMAL_, OPEN_WORK, README), minus any doc a live task, queued task or external claim holds, minus any doc with a line STOP: <reason> in its body (the reason is logged each pass), and minus any doc already deleted on some branch (the DONE ratchet, §4). A doc's class only decides which slots may run it. A re-feed logs what its previous attempt produced.
  3. Continue and retire. Partial work is continued; a dead-on-arrival attempt is retired.
  4. Refill. control.py refill --target N --prefix bug-,fix-; a finished worker frees its slot at once.
  5. Land. Finished bug-*/fix-* branches are merged by tools/integrate.py --stdlib (the stdlib compile is the gate). A conflicting branch goes to a merge-fixer task. After a landing, tools/verify_landed.py runs in the background on master: the full gate, at most once per full_every_minutes; each red job becomes a fix-gate-<job> task. Landed trees are removed by control.py cleanup.

Two other feeders exist and are separate: tools/formal_feed.py owns the FORMAL_ docs (the swarm never starts them), and tools/autointegrate.py is the integrator the swarm calls. Claims (§4) are what keeps the two from colliding, so spawn and enqueue work through control.py, never by editing tasks.json by hand.

A task file is plain text given to spawn --task-file. A good one: states the goal and the docs, names the exact narrow commands, states what must not be touched, and tells the worker to check master. Common closing rules for every worker task:

`python3 tools/memslot.py --gb 8 --label t -- python3 ` (export PATH=/opt/homebrew/bin:$PATH). Lean only via formal/lean.py (time-bounded:
a valid proof is fast; one that is slow is wrong or needs a different formulation). Nothing of ours over 3-4 GB. Read CLAUDE.md first. Commit
often; delete a bug doc you fully fix and run `python3 tools/dangling_doc_refs.py --ratchet`. Finish with a clean tree, a short report, and
CONTROL-STATUS: DONE (or PARTIAL).

Bug-doc worker

Work through these bug docs, in order; each is yours alone:
  - bugs/FOO_a.md
  - bugs/FOO_b.md
Fix each for real (no time-boxing; no "re-verified, unchanged" outcomes; partial progress is committed and the doc's Status updated; a doc stale because the bug is fixed is `git rm`'d).
CHECK MASTER at the start and again before finishing: `git log --oneline master -20`; `git merge master` into your branch before you finish and reconcile.
+ the closing rules

Merger (the hard job; give it to the strongest model)

You are a MERGER. Your branch starts at master. Merge these finished branches into it, oldest first, one at a time, committing each:
  work/a  work/b ...
(For each: `git cherry master ` — only '-' lines means already landed: skip.) Resolve conflicts keeping BOTH sides' intent.
NEVER resolve by taking one whole side when both sides changed a shared signature, import block or definition: keep the branch's half of those.
After EACH merge: `compile()` (not ast.parse) over every `git ls-files '*.py'`, an undefined-name check on the files touched, and the narrow
test_formal_*.py for them. Two competing mechanisms for one construct: satisfy the UNION of both sides' tests and say why in the commit message.
Run `python3 tools/dangling_doc_refs.py --ratchet`. No gate, no bootstrap/mojo/ work. `git merge master` before finishing. CONTROL-STATUS: DONE.

Hard-bug agent

Same as a bug-doc worker, plus: state how correctness is proved (e.g. "byte-identical generated C before and after, cmp the artifacts, plus test_selfhost.py"), say the gate is the controller's, and name which areas belong to another agent.

7. Integration: landing branches on master

  1. Find finished work. status | grep -E 'DONE|PARTIAL' and, authoritative, git for-each-ref --no-merged master --format='%(refname:short)' 'refs/heads/work/*'. Skip branches of workers still running.
  2. Try the plain merge first (in the main checkout, clean tree): git merge --no-edit work/NAME. If it conflicts: git merge --abort and give the branch to a merger. Small conflicts in generated/baseline files (tools/dangling_refs_baseline.py, doc indexes) you can resolve yourself: keep the union, then regenerate with the tool.
  3. After any merge: python3 tools/dangling_doc_refs.py --ratchet (must not gain a citation) and a compile() sweep of every tracked .py (ast.parse misses duplicate arguments).
  4. Verify bulk merges before trusting them: run python3 tools/suite.py check (about 10 minutes) in gate-wt on the branch tip before merging it to master when it is large (the two bulk merges of 374 and 444 commits each left 6 red jobs). Fix forward on master.
  5. Mark landed tasks integrated only after the merge (the feed does this automatically once git rev-list --count master..BRANCH is 0).
  6. Formal-only changes need no gate (owner's rule). Anything touching fire_compiler.py, gimple_codegen.py, mojo/**, runtime/**, module_loader.py, myinterpreter.py owes a full gate (§8) once, after the batch.
  7. Delete fixed bug docs in the same commit as the fix (a doc is a queue entry; a fixed bug listed is indistinguishable from an open one).
Why "resolve to master's side" is dangerous: bulk merges that resolved every conflict to master's side silently dropped the branch's half of shared signatures, import blocks and definitions while keeping the branch's bodies: NameErrors, TypeError: unexpected keyword argument, duplicate definitions, half-applied fixes (a fix landed, a later merge took one side and reverted its test half). Rule: keep both halves; verify with compile(), an undefined-name check, and the narrow tests. See the bulk-merge dropped-definition fix (MERGE bug doc, deleted after fix) for the follow-up queue.

8. The gate and check

tools/suite.py is the only definition of what is tested. python3 tools/suite.py check is the everyday subset (about 53 jobs, ~9-10 min); gate = check + coro + stdlib + native + bootstrap (~35 min, tens of GB). Never restate bucket membership: python3 tools/suite.py --list is the truth. Read CLAUDE.md's "Running the checks", "quality gate" and "Known failures" sections: the markers and rules there are binding.

How to run one

cd /Users/mrs/net/chatgpt/claude/gate-wt && export PATH=/opt/homebrew/bin:$PATH
git checkout -q --detach master            # or the branch tip you want to verify
nohup python3 tools/suite.py check > ../check-X.log 2>&1 &      # or `gate`
# result: last line of ../check-X.log "suite: N passed, M failed ..."; details: gate-wt/build/suite.log
tr -d '\033' < ../check-X.log | awk '/^FAILED/{f=1} f&&/^(EXPECTED|DISABLED|SKIPPED|suite:)/{f=0} f'     # the failing jobs
awk '/--- output: last 40 lines of JOBNAME ---/{f=1} f' build/suite.log | head -40          # one job's output

One gate at a time per machine (memory). Do not touch gate-wt while a run is using it; give hard-problem agents their own worktrees.

Reading it

  • expect='why' = known cheap failure (an expect-marked test that PASSES is reported as a FAILURE: drop the marker). disabled='bugs/DOC.md' = known expensive failure, not run; the doc is the switch (deleting it re-enables the test).
  • Two gate verdicts need judgement beyond exit 0: stdlib-dylib (the count of skip <module>: must not rise) and stdlib-syntax (FAILED: N (E expected, U unexpected): U must not rise).
  • Fanout jobs (bootstrap-stage2-dumps) print many FAIL job:item lines that are absorbed by an expect= count; look at the FAILED section, not those lines.
  • After a gate: if the log prints PEAK DRIFT, run python3 tools/suite.py --apply-peaks build/suite.log [--dry-run] and re-class the jobs it names (only for jobs that PASSED and ran at least 2 s).
  • Flake seen once: x86-examples "toplevel_const: 'LIMIT' has no home" under parallel load; passes alone. Re-run before declaring a regression.
  • Jobs registered but not in check (formal-run, formal-value-model, formal-peephole, test_formal_call_proof_gen.py, ...) are not reported by check; run them narrowly when working in their area.

9. The monitoring loop (every 50 minutes)

The owner asked for a check every 50 minutes (keeps the model prompt cache warm). Each tick, in this order (keep it to a few commands; do not narrate unchanged state):

  1. Fleet: control.py ps; for each running worker compare work.log mtime to now and look at git -C ../work-N rev-list --count master..HEAD and status --short | wc -l. A log untouched for >30 min with ~0% CPU = stalled (§10).
  2. Finished: status | grep -E 'exited|DONE|PARTIAL' and the unmerged-branches list. Land what is finished (§7).
  3. Hard-problem agents: their worktree (.claude/worktrees/agent-*): commits ahead, dirty, behind master. If they stopped on a session limit, try resuming once the stated reset time has passed.
  4. Queue and swarm: tail -3 .git/control/swarm.out (one line per pass, plus every refused start and every landing). Starvation ("skip ... claim conflicts") means unmerged branches are holding claims: land them.
  5. Verification: any pending check/gate log? Read its FAILED section and act (§8).
  6. Resources: df -h / (cleanup above ~85%), load average.
  7. Report to the owner in plain text: what changed, what landed, what is red and why. Never assert a cause without the log line that shows it.

11. Memory, disk, processes

Kill rules (2026-11-02, after the process losses).
  1. The fleet signals only processes it spawned and recorded. Every spawn is written to .git/control/spawned.jsonl with its pid, process group and start time (tools/fleet_ledger.py). Nothing else is ever signalled.
  2. Nothing is matched by working directory, command name or port. A process in a worktree is not ours unless it is in a recorded group.
  3. A user's own opencode session, and anything an outside session has claimed (control.py claim, including a claimed workdir), is never signalled and never removed. cleanup skips such trees.
  4. To stop a recorded worker, the fleet sends SIGTERM to its process group and waits 20 s so the workload can save. SIGKILL is sent only if the group is still alive after that wait. A recorded group whose leader has exited is not signalled; its members are logged and left alone.
  5. A recorded group is stopped only when its leader still has the start time recorded at spawn. A recycled pid is refused.
  6. Every spawn, signal, refusal and skip is appended to .git/control/kills.log. Read it before you decide anything about a process.
  7. Do not signal a process or session by hand. Do not interrupt or delete an opencode session the fleet did not start. If something must stop, ask the owner first.
