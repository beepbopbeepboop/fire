Compiled Coroutine-Body Codegen — Strategy & Plan

Status: APPROVED 2026-09-03 — building Option A3. Supersedes the ad-hoc "widen the C++ emitter one node at a time" approach that produced 8 infra commits (e554064..133742c) this session without fully closing a single bug report. Decision & layered plan in §4–§5; backend bolt-in contract for the deferred GCC frontend work in §7.

Goal (unchanged): professional, high-performance native codegen for Mojo generators (yield) and async def/await, with the same language breadth the ordinary compiled path already has (it compiles the entire 664-file stdlib tree clean).

1. The problem, precisely

The compiler has two independent lowerings of Mojo function bodies:

Ordinary pathCoroutine-body path
Files gimple_codegen.py, gimple_gen_*.py, gimple_module_gen.py (~30k lines) gimple_cpp_core.py (7.3k) + gimple_cpp_async.py (2.9k) = ~10.2k lines
Target language GNU C in -fgimple dialect (three-address, explicitly typed) C++20 text, using co_yield/co_await + a hand-emitted promise_type
Value model Full: every stdlib type, generics, closures, RTTI, tuple-keyed dicts, structseq, … Scalar-centric: int64_t, char *, double, _Bool, plus ad-hoc MojoList * boxing bolted on incrementally
Coverage 664/664 stdlib files compile Refuses (_UnsupportedGeneratorShape) on most non-trivial generators; ~40 open bug reports
How a function reaches it default fn.is_generator or fn.is_async → _gen_cpp_generator_unit() in gimple_module_gen.py; on refusal the whole module falls back to source/interpreter

Every open bug in bugs/ and bugs/hard/ is the same bug: the second lowering does not implement some AST shape that the first lowering handles fine. This session's 9 investigation agents confirmed it — including for the non-generator COMPILE_FAIL_* cluster (socket, contextlib, collections, zipfile, ctypes, the whole Tools/c-analyzer set), which all also refuse inside a coroutine body. The __module__-derived bug titles are mostly stale.

Root cause is architectural, not a pile of small gaps. Widening gimple_cpp_core.py node-by-node is an unbounded task: it is re-deriving, in a second codebase, the language coverage that took years to build in the first. Each bug report needs 2–6 independent value-representation features stacked before it reaches exit 0. The 8 commits this session moved real infrastructure and cut refused-generator counts (e.g. ipaddress 4→2, os.walk's fwalk now compiles) but closed zero reports. That ratio does not improve with more of the same.

2. What is not the problem

  • The "compile both and link" pipeline is fine and live. driver.py _build / compile_linked already compile the coroutine .cpp with g++, link it beside the -fgimple C objects with a C++-aware final driver, and content-address the result. Nothing to "resurrect" — MojoGenerator * = a type-erased std::coroutine_handle<> address, and runtime/mojo_async_runtime.{h,cpp} already has the event loop, timer heap, and fd-wait machinery. The plumbing works; the emitter is the bottleneck.
  • Linking C and C++ is fine. The toolchain split (gcc for -fgimple units, g++ for coroutine units and the final link) is already implemented and gated.

3. The options

Option A — Lower coroutines to plain C as an AST pre-pass (one lowering)

Desugar a generator / async def into ordinary Mojo-level constructs before the normal codegen sees it, so the single broad GIMPLE path lowers everything and the C++ emitter is deleted. Three sub-variants differ only in the suspend mechanism:

A1 — thread per generatorA2 — CPS / state machineA3 — stack-switch coroutine
Mechanism generator body runs on its own pthread; yield = post value + wait on a semaphore; strict cooperative handoff (only one side runs at a time) transform body into a re-entrant switch/computed-goto state machine over a heap frame struct holding all locals + a resume-point int generator body runs on a small heap stack; yield = register-save + stack-pointer swap (aarch64 asm, ~10 ns), à la libaco / boost.context
Language coverage 100% immediately — the body is just ordinary code on its own stack high, but the transform has real hard cases (yield in nested loop, in expression position, across try/finally, yield from) 100% immediately — same as A1
Perf cost per yield ~0.5–1 µs context switch; ~8–64 KB stack per live generator a few loads + an indirect jump; frame is exactly the locals ~10 ns; ~4–16 KB stack per live generator
Implementation size ~small: a runtime shim + a thin lowering; mirrors the interpreter's existing _ThreadedGenerator large: the transform is the classic hard part of every generator compiler medium: per-arch asm (aarch64 for M5, x86-64 for CI) + a thin lowering
Precedent in this repo myinterpreter.py already ships exactly this (_ThreadedGenerator, thread + Event handoff) — —
Deletes gimple_cpp_*? Yes — all ~10.2k lines of the second lowering, and the _UnsupportedGeneratorShape fallback maze with it

A1 and A3 are the same lowering with a swappable primitive: "run the body to the next suspension point on a side context, marshal the yielded value across." Start with A1 (portable, trivially debuggable, matches the interpreter), swap in A3's stack-switch primitive later for perf without touching the lowering or the language coverage. async/await is the same transform with the suspension returning to the mojo_async_runtime event loop instead of the caller.

Cooperative-only threading keeps the "single-threaded runtime" invariant honest. Generator threads never run concurrently with each other or with the main thread — every yield/resume is a strict baton pass. No shared-data locking is introduced; the runtime's grep-confirmed lock-free assumptions hold. (This is precisely the interpreter's current model.)

Option B — Feed the ordinary lowering into the C++ emitter

Keep C++ coroutines for frame/suspend; stop hand-writing expression/statement lowering by having _cpp_stmt/_cpp_expr call the same logic the ordinary path uses. Blocked: the ordinary path emits GIMPLE tuples, not C++ expressions, and g++ does not accept -fgimple. There is no cheap bridge; making the C++ emitter consume GIMPLE is Option C.

Option C — Coroutine-lowering pass in the GNU Mojo frontend (the endgame)

~/net/gcc (branch mrs-mojo) has a real GCC Mojo frontend: gcc/mojo/ ~4.9k lines plus mojo-gimple-bridge.cc (a C/Python GIMPLE-builder FFI). GCC's middle-end already carries the coroutine machinery the C++ frontend drives — the ramp/resume/destroy split and the __builtin_coro_* intrinsics. A Mojo-frontend coroutine pass modelled on gcc/cp/coroutines.cc (5.6k lines) would drive the same builtins from Mojo GENERIC/GIMPLE.

  • Upside: native, fully optimized, LTO-transparent coroutines; no textual C++; retires the Python C++ emitter and is a step toward retiring the printf-GIMPLE approach entirely.
  • Cost: the specialized worktree layout described below; building GCC; real frontend/middle-end work. Weeks–months, one dedicated owner.
  • Worktree layout required: a clean master tree + Iain's M5 port (mainline GCC does not target Apple M5 — mrs-m5 adds it) as the base, then a fresh feature-development branch in its own worktree. Do not develop this on mrs-mojo directly.

Option D — LTO across the C/C++ boundary

Compile every unit (-fgimple C and coroutine C++) with -flto so the cross-language boundary dissolves at link time: a single-client coroutine's frame ops get inlined into its C caller, giving "the appearance of coroutines in C" in the final binary. Orthogonal: it improves codegen quality for whatever the emitter produces, but does not add one line of language coverage. Worth doing on its own merits and compatible with A, C, or the status quo.

Option E — "just compile both" path

Already implemented and live (§2). Nothing to do.

4. Decision (2026-09-03)

Selected: Option A3 — stack-switch coroutines, in-tree. One lowering (the ordinary broad GIMPLE path), a small architecture-isolated context-switch primitive, and a narrow backend seam so the GCC Mojo-frontend implementation (Option C, deferred to a separate effort) can later be bolted in under the same contract without touching the lowering or any consumer.

  • 100% language coverage — a generator/async body runs as ordinary code on its own stack; the ordinary codegen lowers it, so everything that compiles the stdlib works.
  • Most of the performance — a yield is a register-save + stack-pointer swap (~10 ns on aarch64), not a µs-scale thread hop.
  • Stays in this tree — no libpthread dependency, no GCC build, no second toolchain beyond what generic-instantiation C++ already needs.
  • Deletes ~10.2k lines — gimple_cpp_core.py + gimple_cpp_async.py and the _UnsupportedGeneratorShape fallback maze.

Deferred to a separate effort (the other AI): Option C — the GCC Mojo frontend coroutine pass. This plan's job is to make that a clean bolt-in: see §7, the backend ABI. Option D (LTO) stays an independent, any-time codegen-quality workstream.

5.2 Phase 1 — Layer 3, context switch (runtime/mojo_coro_ctx_aarch64.S)

The boost.context / libaco fcontext ABI — the minimal, proven shape. Written from the AAPCS64 spec (callee-saved x19–x28, x29/x30, v8–v15, sp), not copied, to keep provenance clean.

/* runtime/mojo_coro_ctx.h  --  SEAM B : the entire arch-specific surface */
typedef void *mojo_fctx_t;                 /* opaque: saved SP at top of some stack */
typedef struct { mojo_fctx_t from; void *data; } mojo_xfer_t;

/* build a context at the top of [stack, stack+size) that enters fn(xfer) on first jump */
mojo_fctx_t mojo_make_fctx(void *stack_top, size_t size, void (*fn)(mojo_xfer_t));
/* save current context, switch to `to`, deliver `data`; returns when jumped back to */
mojo_xfer_t mojo_jump_fctx(mojo_fctx_t to, void *data);
/* jump to `to` but first run fn on `to`'s stack — used for unwind-on-destroy */
mojo_xfer_t mojo_ontop_fctx(mojo_fctx_t to, void *data, mojo_xfer_t (*fn)(mojo_xfer_t));

~80 lines aarch64. No heap, no libc, no OS calls — pure register shuffling. Unit-tested in isolation (runtime/test_mojo_coro_ctx.c) before anything above it exists.

5.3 Phase 2 — Layer 2, coroutine runtime (runtime/mojo_coro.c)

Arch-independent C on top of Seam B. Public API = Seam A (callable from -fgimple):

typedef struct MojoCoro MojoCoro;

/* stack: mmap'd with a guard page; size from MOJO_CORO_STACK env or a 256 KB default */
MojoCoro *__mojo_coro_new(void (*body)(MojoCoro *, void *env), void *env, size_t stack);
/* 1 = suspended at a yield (*out = yielded box); 0 = body returned (*out = return box) */
int       __mojo_coro_resume(MojoCoro *c, int64_t send_box, int64_t *out);
/* called only from inside `body`: hands `val` to the resumer, returns the next send box  */
int64_t   __mojo_coro_yield(MojoCoro *c, int64_t val);
int64_t   __mojo_coro_return_value(MojoCoro *c);
/* inject a typed exception at the suspension point; same return contract as _resume       */
int       __mojo_coro_throw(MojoCoro *c, void *exc, int64_t *out);
/* if still live, resume it with a GeneratorExit sentinel so with/finally unwind, then free */
void      __mojo_coro_destroy(MojoCoro *c);
  • Strictly one-at-a-time. Exactly one of {resumer, body} runs at any moment — a baton pass, never concurrency. The runtime's grep-confirmed "single-threaded, no locks" invariant is preserved; no user data is ever shared across a race.
  • Values are one int64_t box (scalar bits or a pointer) — the universal tagged box the ordinary path already uses for Variant/RTTI. Layer 1 records the concrete yield/return type in _generator_api (already has _generator_yield_ctype) so consumers unbox at the right type.
  • Exceptions. The trampoline wraps body() in the existing typed-exception landing pad; an escaped exception is stashed and re-raised from __mojo_coro_resume in the resumer's context. __mojo_coro_throw stashes then resumes; __mojo_coro_yield's return path checks the stash and raises in the body's context.
  • GeneratorExit / destroy. __mojo_coro_destroy on a live coroutine uses mojo_ontop_fctx to raise a private _MojoGenClose at the suspension point so with / try-finally run, mirroring CPython's GeneratorExit. Then unmaps the stack.
  • async. Same object; for an async def the "resumer" is the mojo_async_runtime scheduler. await x drives x's handle, then __mojo_coro_yields a "not ready, wake me on E" token the loop understands (reusing the timer-heap / fd-wait facilities already in mojo_async_runtime.h). Async generators use both rewrites.

5.4 Phase 3 — Layer 1, lowering (gimple_gen_coro.py)

For fn g(p0, p1) -> T containing yield (arch- and backend-independent; emits only the Seam-A names):

  • Env struct __g_env { P0 p0; P1 p1; } — arguments only. Body locals live on the coroutine's real stack (the point of A3): no frame struct, no escape analysis, no per-local hoisting.
  • Trampoline void __g_body(MojoCoro *__c, void *__e): unpack __e → real params, then the original body, lowered by the ordinary path, with only these local rewrites:
    • yield e → __mojo_coro_yield(__c, __box<T>(e)) (statement position: discard result)
    • x = yield e / x = (yield e) → x = __unbox(__mojo_coro_yield(__c, __box<T>(e)))
    • yield from it → for __v in it: __send = __mojo_coro_yield(__c, __v) with .send()/.throw() forwarding and StopIteration.value capture
    • return e → __c->ret = __box<T>(e); return;
    • await e (async) → the drive-then-suspend sequence in §5.3
    No control-flow transformation — nested loops, try/finally, with, match, comprehensions containing yield all Just Work because they are lowered by the ordinary path on a real stack.
  • Factory MojoGenerator *g(p0, p1): heap a __g_env, __mojo_coro_new(__g_body, env, 0), wrap in today's exact MojoGenerator * handle. Every consumer — for x in g(...), next(), .send(), _generator_api, cross-module __mojo_reflect — is byte-for-byte unchanged.

7. Seam A — the backend ABI (the Option C bolt-in contract)

Version coro-abi/1. Layer 1 emits exactly these six primitives and nothing else that is coroutine-specific. A backend is any implementation of them. The in-tree backend is runtime/mojo_coro.c (§5.3); the GCC Mojo-frontend backend (Option C) recognizes the same six as intrinsics and lowers them to __builtin_coro_*.

PrimitiveSemantics (identical across backends)
MojoCoro *__mojo_coro_new(body, env, stack) Create a suspended coroutine. body is void(MojoCoro*, void*); env is an opaque heap pointer the caller owns until the coroutine is destroyed; stack 0 = backend default. No code runs yet.
int __mojo_coro_resume(c, send_box, int64_t *out) Run c from its suspension point (first call: from the top of body; send_box ignored on the first call). Returns 1 and sets *out to the yielded box if it hit __mojo_coro_yield; returns 0 and sets *out to the return box if body returned. If body raised, re-raises in the caller's context. Precondition: c is suspended (not running, not done).
int64_t __mojo_coro_yield(c, val_box) Callable only lexically within body. Suspends c, delivers val_box to the matching _resume/_throw. Returns the next send_box. May raise (a pending _throw/_destroy exception) instead of returning.
int64_t __mojo_coro_return_value(c) Valid only after _resume/_throw returned 0. The return box.
int __mojo_coro_throw(c, void *exc, int64_t *out) Like _resume but the suspended __mojo_coro_yield raises exc (a typed-exception object) instead of returning a send value. Same return contract.
void __mojo_coro_destroy(c) If c is suspended, resume it once with a _MojoGenClose raised at the suspension point (so finally/with run); swallow _MojoGenClose and StopIteration escaping that unwind, propagate anything else. Then release all backend resources. Idempotent on an already-done coroutine.

Handle ABI: the factory returns today's MojoGenerator * (a __mojo_reflect-visible opaque). Its next/send/throw/close entry points forward 1:1 to _resume/_resume/_throw/_destroy. Unchanged from the current C++20-coroutine implementation — that is what makes the backend swap invisible to every consumer.

Reverse direction (for the Option C context): the GCC frontend needs, from this side, only (a) this table's semantics, (b) the MojoGenerator * handle layout (documented in runtime/mojo_async_runtime.h), and (c) the box convention (doc/ABI.md). No Python, no mojo_coro.c. A conforming __builtin_coro_* lowering of the six primitives is a drop-in replacement for Layer 2.
